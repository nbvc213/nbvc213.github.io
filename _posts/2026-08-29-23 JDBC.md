## JDBC 概述

### 什么是 JDBC

**JDBC（Java Database Connectivity，Java 数据库连接）是 Java 提供的一套访问数据库的标准 API 和规范。** Java 程序可以通过 JDBC 建立数据库连接、发送 SQL 语句、获取执行结果，从而完成对数据库中数据的增删改查。

在数据库客户端或命令行中操作数据库时，通常是直接向数据库服务器发送 SQL，例如：

```sql
SELECT * FROM t_user;
```

使用 JDBC 后，则由 Java 程序通过 JDBC API 将 SQL 发送给数据库服务器，基本关系可以表示为：

```text
Java 程序 → JDBC API → JDBC 驱动 → 数据库服务器
```

因此，JDBC 本身并不负责存储数据，也不是数据库，而是 **Java 程序与数据库之间进行交互的一套标准机制**。

> **注意**
>
> 严格来说，不能简单理解为“JDBC 就是一组接口”。JDBC 是一套数据库访问规范和 API，其中既包含 `Connection`、`Statement`、`ResultSet`、`Driver` 等接口，也包含 `DriverManager` 等类。学习 JDBC 原理时，可以重点理解为：**Java 定义统一标准，数据库厂商负责提供具体实现。**

------

### JDBC 的工作原理

不同数据库的内部实现和通信协议存在差异。例如 MySQL、Oracle 等数据库在连接方式、网络协议和底层实现方面并不完全相同。

如果 Java 程序直接针对不同数据库编写代码，那么使用 MySQL 时需要编写一套代码，切换到 Oracle 后又需要修改大量代码，程序会与具体数据库严重耦合。

为解决这一问题，JDBC 采用了**面向接口编程**的设计思想：

1. Java 最初由 Sun 公司制定统一的 JDBC 规范，规定 Java 程序应该通过哪些标准 API 操作数据库。
2. MySQL、Oracle 等数据库厂商按照 JDBC 规范提供自己的具体实现。
3. 数据库厂商提供的这些实现通常被称为 **JDBC 驱动（JDBC Driver）**。
4. Java 程序主要面向 JDBC 标准 API 编程，而不直接依赖数据库厂商内部的具体实现。

因此，JDBC 中可以理解为存在三个主要角色：

| 角色            | 作用                             | 典型内容                              |
| --------------- | -------------------------------- | ------------------------------------- |
| JDBC 规范制定者 | 定义统一的数据库访问标准         | Java JDBC API                         |
| JDBC 驱动提供者 | 实现 JDBC 标准，与具体数据库通信 | MySQL Connector/J、Oracle JDBC Driver |
| JDBC 调用者     | 使用 JDBC API 操作数据库         | Java 应用程序                         |

核心关系可以表示为：

```text
                     JDBC 规范
                        ↓
Java 程序 → JDBC 标准 API ← MySQL 驱动
                        ↑
                        └── Oracle 驱动
```

例如，Java 程序获取数据库连接后，通常使用 `Connection conn` 保存连接对象，其中 `Connection` 是 `java.sql.Connection` 接口。

如果连接的是 MySQL，运行时真正创建的对象由 MySQL JDBC 驱动提供；如果以后切换为 Oracle，则会由 Oracle 驱动提供对应的实现对象。Java 程序后续仍然可以通过 `conn.createStatement()` 等 JDBC 标准方法操作数据库，而不需要知道 `conn` 具体属于哪个数据库厂商的实现类。

这正是**面向接口编程**带来的好处：调用者只依赖稳定的 JDBC 标准，而具体实现可以发生变化，从而降低 Java 程序与具体数据库之间的耦合。

------

### 用接口模拟 JDBC 的设计思想

JDBC 的核心设计思想可以通过一个简化模型理解。

假设规定所有数据库连接器都必须提供一个 `connect()` 方法，可以定义统一接口：

```java
public interface DatabaseConnector {

    void connect();
}
```

MySQL 厂商按照该标准提供实现：

```java
public class MySQLConnector implements DatabaseConnector {

    @Override
    public void connect() {
        System.out.println("连接 MySQL 数据库");
    }
}
```

Oracle 厂商也可以实现同一个接口：

```java
public class OracleConnector implements DatabaseConnector {

    @Override
    public void connect() {
        System.out.println("连接 Oracle 数据库");
    }
}
```

Java 程序使用接口类型接收具体实现对象：

```java
DatabaseConnector connector = new MySQLConnector();
connector.connect();
```

此时形成如下关系：

```text
DatabaseConnector
       ↑
       ├── MySQLConnector
       └── OracleConnector
```

调用者只需要知道 `DatabaseConnector` 规定了哪些方法，并不需要知道不同数据库内部怎样完成连接。

这体现了接口在 JDBC 中最重要的作用：**接口在调用者和实现者之间建立统一标准，使双方彼此解耦。**

不过，`DatabaseConnector connector = new MySQLConnector();` 中仍然直接出现了 `MySQLConnector`，因此 Java 程序仍然依赖具体实现。如果以后切换为 Oracle，就需要将其修改为 `DatabaseConnector connector = new OracleConnector();`。

如果希望进一步降低这种依赖，可以将具体实现类写入配置文件，再通过反射动态创建对象。

例如，在 `jdbc.properties` 中配置：

```properties
driver=com.example.MySQLConnector
```

Java 程序读取配置并通过反射创建对象：

```java
import java.util.ResourceBundle;

public class Client {

    public static void main(String[] args) throws Exception {

        String className =
                ResourceBundle.getBundle("jdbc").getString("driver");

        Class<?> clazz = Class.forName(className);

        DatabaseConnector connector =
                (DatabaseConnector) clazz.getDeclaredConstructor().newInstance();

        connector.connect();
    }
}
```

以后需要切换数据库时，只需要修改配置文件：

```properties
driver=com.example.OracleConnector
```

Java 主程序不需要修改。

这种设计进一步体现了**开闭原则（Open-Closed Principle，OCP）**的思想：对于功能扩展尽量开放，对于已有代码修改尽量关闭。

> **注意**
>
> 上述 `DatabaseConnector` 只是为了理解 JDBC 原理而设计的模拟接口，JDK 中并不存在一个名称为 `JDBC` 或 `DatabaseConnector` 的统一接口。真正的 JDBC 由 `Driver`、`Connection`、`Statement`、`ResultSet` 等多个接口和相关类共同组成。

------

### JDBC API 与数据库驱动

完成 JDBC 开发至少需要两个方面的内容：**JDK 提供的 JDBC API**和**数据库厂商提供的 JDBC 驱动**。

#### JDBC API

JDBC 的核心 API 已经包含在 JDK 中，主要位于 `java.sql` 包。

常用类型包括：

| 类型            | 类型性质 | 主要作用                             |
| --------------- | -------- | ------------------------------------ |
| `Driver`        | 接口     | JDBC 驱动需要遵循的基本标准          |
| `DriverManager` | 类       | 管理 JDBC 驱动并负责获取数据库连接   |
| `Connection`    | 接口     | 表示 Java 程序与数据库之间的一次连接 |
| `Statement`     | 接口     | 用于执行 SQL 语句                    |
| `ResultSet`     | 接口     | 保存查询得到的结果集                 |

因此，只要安装了 JDK，就已经拥有 JDBC API，不需要另外下载。

#### JDBC 驱动

JDK 提供的是统一标准，但并不知道如何与某一种具体数据库进行底层通信，因此还需要数据库厂商提供 JDBC 驱动。例如 MySQL 使用 **MySQL Connector/J**，Oracle 使用 **Oracle JDBC Driver**。

驱动一般以 `.jar` 文件的形式提供，其中包含大量已经编译完成的 `.class` 文件。这些类负责实现 JDBC 规范，并完成与具体数据库之间的通信。

因此，**只有 JDBC API，没有对应数据库的 JDBC 驱动，Java 程序仍然无法连接具体数据库。**

二者的关系可以简单理解为：

```text
JDK
└── java.sql
    └── JDBC 标准 API

MySQL Connector/J
└── JDBC 标准的 MySQL 实现

Oracle JDBC Driver
└── JDBC 标准的 Oracle 实现
```

------

### 将 JDBC 驱动加入 Classpath

数据库驱动本质上是一个 JAR 包。Java 程序在编译或运行时必须能够找到驱动中的类，因此需要将驱动 JAR 加入程序的 **Classpath（类路径）**。

如果使用命令行开发，可以通过 `CLASSPATH` 环境变量或者 `-cp` 参数指定驱动 JAR。例如在 Windows 环境中，可以将类路径设置为 `.;lib\mysql-connector-j-x.x.x.jar`。

其中 `.` 表示当前目录。如果自己编写的 `.class` 文件位于当前目录，而设置 `CLASSPATH` 时没有包含 `.`，JVM 可能无法找到自己的程序类。

也可以在执行 Java 程序时直接通过 `-cp` 指定：

```text
java -cp ".;lib\mysql-connector-j-x.x.x.jar" JDBCTest
```

如果使用 IDEA，一般不需要手动配置系统环境变量 `CLASSPATH`。可以在项目中创建 `lib` 目录保存 JDBC 驱动 JAR，然后通过 **Add as Library** 将 JAR 注册为 IDEA Library，并确保**实际运行 JDBC 代码的 Module 已将该 Library 添加到 `Dependencies` 中**。如果一个 Project 中包含多个 Module，需要特别注意驱动 JAR 是否添加到了正确的 Module。

这些操作本质上解决的是同一个问题：**让 JVM 在编译或运行程序时能够找到 JDBC 驱动中的类。**

## JDBC 编程六步

JDBC 最基础的编程流程可以概括为六步：

| 步骤 | 主要任务             | 核心 API                               |
| ---- | -------------------- | -------------------------------------- |
| 1    | 加载、注册 JDBC 驱动 | `Driver`、`DriverManager`              |
| 2    | 获取数据库连接       | `Connection`                           |
| 3    | 获取数据库操作对象   | `Statement`                            |
| 4    | 执行 SQL             | `executeUpdate()`、`executeQuery()` 等 |
| 5    | 处理查询结果集       | `ResultSet`                            |
| 6    | 释放 JDBC 资源       | `close()`、try-with-resources          |

整体流程为：

```text
加载、注册驱动
      ↓
获取 Connection
      ↓
获取 Statement
      ↓
    执行 SQL
      ↓
如果是查询 → 处理 ResultSet
      ↓
释放 ResultSet、Statement、Connection
```

其中，第五步只有执行查询并产生结果集时才需要。例如执行 `INSERT`、`DELETE` 或 `UPDATE` 时通常不会得到 `ResultSet`，因此可以跳过第五步。

------

### 第一步：注册 JDBC 驱动

驱动注册的目的是**让 JDBC 管理层能够发现并使用对应的数据库驱动**。当程序以后根据 JDBC URL 请求数据库连接时，`DriverManager` 才能够找到可以处理该 URL 的驱动。

最直接的教学写法是：

```java
Driver driver = new com.mysql.cj.jdbc.Driver();
DriverManager.registerDriver(driver);
```

完整形式如下：

```java
import java.sql.Driver;
import java.sql.DriverManager;
import java.sql.SQLException;

public class JDBCTest {

    public static void main(String[] args) {

        try {
            Driver driver = new com.mysql.cj.jdbc.Driver();
            DriverManager.registerDriver(driver);
        } catch (SQLException e) {
            e.printStackTrace();
        }
    }
}
```

这里的 `Driver` 指 `java.sql.Driver`，属于 JDBC 标准接口；`com.mysql.cj.jdbc.Driver` 则是 MySQL Connector/J 提供的具体实现类。

代码中使用完整类名 `com.mysql.cj.jdbc.Driver`，一方面可以明确指定 MySQL 驱动中的实现类，另一方面可以避免它与 `java.sql.Driver` 发生名称混淆。

因此，`Driver driver = new com.mysql.cj.jdbc.Driver();` 本质上仍然属于典型的“**接口类型引用指向实现类对象**”，体现了多态和面向接口编程。

不过，这种显式调用 `DriverManager.registerDriver()` 的方式主要适合理解 JDBC 原理。**从 JDBC 4.0 开始，只要符合规范的 JDBC 驱动已经正确加入 Classpath，`DriverManager` 通常可以自动发现和加载驱动，不再需要程序员手动注册。**

因此，现代 JDBC 程序中通常可以直接从获取数据库连接开始：

```java
Connection conn =
        DriverManager.getConnection(url, user, password);
```

> **结论**
>
> “注册驱动”仍然是理解 JDBC 工作流程的重要一步，但在 JDBC 4.0 及之后的正常项目中，只要驱动 JAR 已正确加入 Classpath，通常不需要再显式编写驱动注册代码。

------

### 第二步：获取数据库连接

Java 程序通过 `DriverManager.getConnection()` 建立数据库连接。例如：

```java
String url = "jdbc:mysql://localhost:3306/jdbc";
String user = "root";
String password = "123456";

Connection conn =
        DriverManager.getConnection(url, user, password);
```

`getConnection()` 返回一个 `java.sql.Connection` 类型的对象。

`Connection` 可以理解为 **Java 应用程序与某个数据库之间建立的一次连接会话**。后续 SQL 的执行、事务控制等操作都需要建立在数据库连接之上。

变量 `conn` 的声明类型是 JDBC 标准接口 `Connection`，真正创建的对象则由具体数据库驱动提供。如果使用 MySQL，底层会得到 MySQL Connector/J 提供的实现对象；如果切换为 Oracle，具体实现对象也会发生变化。

Java 程序本身仍然通过 `Connection` 接口进行操作，不需要依赖具体实现类，这也是 JDBC 面向接口编程的重要体现。

#### JDBC URL

建立数据库连接通常需要提供**数据库 URL、用户名和密码**三个基本信息。用户名和密码用于数据库身份认证，而 **JDBC URL 用于描述需要连接哪一种数据库、哪一台服务器以及哪一个数据库。**

MySQL 中最常见的 JDBC URL 格式为：

```text
jdbc:mysql://主机地址:端口号/数据库名称
```

例如：

```text
jdbc:mysql://localhost:3306/jdbc
```

可以拆解为：

| 部分            | 含义                     |
| --------------- | ------------------------ |
| `jdbc:mysql://` | 表示使用 JDBC 连接 MySQL |
| `localhost`     | MySQL 所在主机           |
| `3306`          | MySQL 服务端口           |
| `jdbc`          | 要连接的数据库名称       |

其中，`localhost` 表示本机，也经常可以写成 `127.0.0.1`；MySQL 默认端口通常为 `3306`。

> **易错点**
>
> `jdbc:mysql://localhost:3306/jdbc` 最后的 `jdbc` 是 **MySQL 数据库名称**，不宜称为“MySQL 实例名”。“实例”在不同数据库产品中的含义并不完全相同，学习 MySQL JDBC 时直接理解为“要连接的数据库”更加准确。

#### JDBC URL 的连接参数

JDBC URL 后面还可以使用 `?参数名=参数值` 添加连接参数，如果存在多个参数，则通过 `&` 连接，例如：

```text
jdbc:mysql://localhost:3306/jdbc?key1=value1&key2=value2
```

MySQL Connector/J 支持大量连接属性，不同驱动版本支持的属性及其默认行为可能存在差异，因此不应把某一套 URL 参数组合死记成“所有 JDBC 程序都必须这样配置”。

常见参数主要用于解决**时区、连接安全和字符编码**等问题。

**1. 时区设置**

旧版教学资料中经常使用 `serverTimezone=Asia/Shanghai`，例如：

```text
jdbc:mysql://localhost:3306/jdbc?serverTimezone=Asia/Shanghai
```

在较新的 Connector/J 中，还可以使用 `connectionTimeZone` 描述连接时区。从 Connector/J 8.0.23 开始，`serverTimezone` 可以作为 `connectionTimeZone` 的别名。

这类参数主要影响 JDBC 驱动处理需要进行时区转换的日期时间数据时所采用的时区。

**2. SSL/TLS 安全连接**

传统 JDBC URL 中经常使用 `useSSL=true` 控制是否通过 SSL/TLS 加密数据库连接。较新的 Connector/J 中还可以通过 `sslMode` 对 SSL/TLS 连接方式进行更详细的控制。

例如，连接模式可能涉及 `PREFERRED`、`REQUIRED`、`VERIFY_CA` 或 `VERIFY_IDENTITY` 等配置。

因此，不能简单理解为 **`useSSL=true` 就一定代表连接已经达到充分的安全状态**。实际安全程度还与是否验证服务器证书、采用哪种 SSL 模式以及服务器自身配置有关。

**3. 字符编码**

旧版示例中经常同时配置 `useUnicode=true` 和 `characterEncoding=UTF-8`。

不应简单将二者理解为“`useUnicode` 决定传输过程中是否使用 Unicode，而 `characterEncoding` 决定数据到服务器以后采用什么编码”。这种解释并不准确。

Java 中的字符串本身使用 Unicode 表示。MySQL Connector/J 会负责在 Java 字符串与数据库连接采用的字符编码之间进行转换，`characterEncoding` 主要影响 **JDBC 客户端与 MySQL 服务器之间连接所使用的字符编码**。

因此，现阶段重点理解即可：**字符编码相关参数主要用于保证 Java 程序与数据库之间能够正确进行字符编码转换，避免中文等字符在传输和存储过程中出现乱码。**

> **注意**
>
> JDBC URL 中的时区、安全和字符编码等参数与 Connector/J 的具体版本有关。学习阶段应重点掌握这些参数分别解决什么问题，而不要机械记忆某一个固定 URL。实际项目中应根据使用的驱动版本确定具体配置。

------

### 第三步：获取数据库操作对象

成功获得 `Connection` 后，需要创建负责执行 SQL 的数据库操作对象。当前阶段最基础的是 `java.sql.Statement` 接口，可以通过 `conn.createStatement()` 获取：

```java
Statement stmt = conn.createStatement();
```

`Statement` 同样属于 JDBC 标准接口。真正创建出的实现对象由数据库驱动提供，但 Java 程序通常只需要通过 `Statement` 接口操作它。

`Connection` 与 `Statement` 的职责可以简单理解为：

```text
Connection
    ↓
表示数据库连接
    ↓
createStatement()
    ↓
Statement
    ↓
负责执行 SQL
```

因此，`Connection` 主要解决“**Java 程序通过哪一个数据库连接进行操作**”，而 `Statement` 负责“**通过这个连接执行 SQL**”。

同一个 `Connection` 可以创建多个不同的 `Statement` 对象，例如：

```java
Statement stmt1 = conn.createStatement();
Statement stmt2 = conn.createStatement();
```

`stmt1` 和 `stmt2` 是两个不同的数据库操作对象，但都建立在同一个数据库连接之上。

------

### 第四步：执行 SQL

获得 `Statement` 后，就可以通过它执行 SQL。当前阶段最重要的方法之一是 `executeUpdate(String sql)`。

例如：

```java
String sql =
        "update t_user set password = '654321' where id = 3";

int count = stmt.executeUpdate(sql);
```

`executeUpdate()` 在当前阶段主要用于执行 `INSERT`、`DELETE` 和 `UPDATE` 等数据修改语句，其返回值类型为 `int`，表示 SQL 执行后影响的记录条数。

例如，如果 `count` 的值为 `1`，说明有 1 条记录受到影响；如果值为 `3`，说明有 3 条记录受到影响。

因此，可以根据返回值判断本次 SQL 实际影响了多少条数据：

```java
if (count > 0) {
    System.out.println("操作成功");
} else {
    System.out.println("没有记录受到影响");
}
```

查询语句 `SELECT` 通常不会通过 `executeUpdate()` 获取查询数据，而是使用 `executeQuery()` 执行，并得到一个 `ResultSet` 查询结果集。

| SQL 类型                     | 常用方法          | 典型返回值  |
| ---------------------------- | ----------------- | ----------- |
| `INSERT`、`DELETE`、`UPDATE` | `executeUpdate()` | `int`       |
| `SELECT`                     | `executeQuery()`  | `ResultSet` |

------

### 第五步：处理查询结果集

执行 `SELECT` 查询语句后，数据库会返回查询结果，JDBC 通常使用 `java.sql.ResultSet` 对查询结果进行封装。

例如：

```java
String sql = "select id, name from t_user";
ResultSet rs = stmt.executeQuery(sql);
```

假设查询得到：

| id   | name |
| ---- | ---- |
| 1    | 张三 |
| 2    | 李四 |
| 3    | 王五 |

`ResultSet` 内部可以理解为存在一个**游标（cursor）**。结果集刚创建时，游标位于第一条记录之前，需要调用 `next()` 才能移动到下一条记录。

典型遍历方式为：

```java
while (rs.next()) {
    int id = rs.getInt("id");
    String name = rs.getString("name");

    System.out.println(id + " " + name);
}
```

`next()` 每调用一次，游标就尝试向下一行移动：

```text
初始位置
   ↓
第一行
   ↓
第二行
   ↓
第三行
   ↓
结果集末尾
```

如果成功移动到下一条记录，`rs.next()` 返回 `true`；如果已经没有下一条记录，则返回 `false`。因此，它非常适合与 `while` 循环配合完成结果集遍历。

如果执行的是 `INSERT`、`DELETE` 或 `UPDATE`，通常不会产生需要遍历的查询结果集，因此 JDBC 六步中的第五步可以跳过。

------

### 第六步：释放 JDBC 资源

JDBC 中的 `Connection`、`Statement` 和 `ResultSet` 都属于需要及时关闭的资源。

它们不仅仅对应普通 Java 对象，底层还可能关联数据库连接、网络 Socket、数据库游标等外部资源。如果长期不释放，可能导致数据库连接等资源被持续占用，最终出现连接耗尽等**资源泄漏**问题。

因此，**JDBC 资源使用完成后必须及时关闭。**

资源关闭顺序通常与创建顺序相反。创建时通常按照 `Connection → Statement → ResultSet` 的顺序获得资源，因此释放时通常按照 `ResultSet → Statement → Connection` 的顺序关闭：

```java
rs.close();
stmt.close();
conn.close();
```

之所以采用反向关闭，是因为后创建的资源通常依赖先创建的资源。例如 `ResultSet` 依赖 `Statement`，`Statement` 又依赖 `Connection`，因此应先关闭依赖层次更深的资源。

#### 使用 finally 释放资源

传统 JDBC 写法通常先在 `try` 外部声明资源：

```java
Connection conn = null;
Statement stmt = null;
ResultSet rs = null;
```

然后在 `finally` 中按照相反顺序关闭：

```java
finally {

    if (rs != null) {
        try {
            rs.close();
        } catch (SQLException e) {
            e.printStackTrace();
        }
    }

    if (stmt != null) {
        try {
            stmt.close();
        } catch (SQLException e) {
            e.printStackTrace();
        }
    }

    if (conn != null) {
        try {
            conn.close();
        } catch (SQLException e) {
            e.printStackTrace();
        }
    }
}
```

使用 `finally` 的原因是：即使 `try` 中执行 SQL 时发生异常，程序通常仍然会执行对应的 `finally`，从而尽量保证资源最终被释放。

关闭各个资源时分别进行异常处理，可以避免前一个资源关闭失败后，导致后面的资源没有机会继续关闭。

#### 使用 try-with-resources

Java 7 开始提供 **try-with-resources** 语法，可以自动管理资源。

例如：

```java
try (
        Connection conn =
                DriverManager.getConnection(url, user, password);

        Statement stmt =
                conn.createStatement()
) {

    String sql =
            "update t_user set password = '654321' where id = 3";

    int count = stmt.executeUpdate(sql);

    System.out.println("影响记录数：" + count);

} catch (SQLException e) {
    e.printStackTrace();
}
```

当程序离开 `try` 代码块后，在资源声明区域创建的 `stmt` 和 `conn` 会自动关闭，因此不再需要手动编写 `stmt.close()` 和 `conn.close()`。

`Connection`、`Statement` 和 `ResultSet` 都可以使用 try-with-resources 管理，因此在实际 JDBC 开发中可以显著减少手动资源释放代码。

> **注意**
>
> JDBC 资源不能简单依赖 JVM 的垃圾回收机制。垃圾回收主要负责 Java 堆中对象的生命周期管理，不能保证数据库连接、网络连接等外部资源能够在需要的时间及时释放。因此 JDBC 编程必须主动管理并关闭资源。

> **结论**
>
> 传统的 `finally + close()` 写法有助于理解 JDBC 资源管理的基本原理；实际编写代码时，如果当前 Java 版本允许，通常优先使用 try-with-resources，使代码更加简洁，并降低遗漏资源关闭操作的风险。

------

### JDBC 基本操作完整流程

以执行一条 `UPDATE` 语句为例，使用 try-with-resources 可以将 JDBC 基本操作写为：

```java
import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.SQLException;
import java.sql.Statement;

public class JDBCTest {

    public static void main(String[] args) {

        String url = "jdbc:mysql://localhost:3306/jdbc";
        String user = "root";
        String password = "123456";

        try (
                // 2. 获取数据库连接
                Connection conn =
                        DriverManager.getConnection(url, user, password);

                // 3. 获取数据库操作对象
                Statement stmt =
                        conn.createStatement()
        ) {

            // 4. 执行 SQL
            String sql =
                    "update t_user set password = '654321' where id = 3";

            int count = stmt.executeUpdate(sql);

            System.out.println("影响记录数：" + count);

        } catch (SQLException e) {
            e.printStackTrace();
        }
    }
}
```

从逻辑上看，这段程序仍然符合 JDBC 六步：

1. **注册驱动**：JDBC 4.0 之后通常由驱动自动发现机制完成。
2. **获取数据库连接**：通过 `DriverManager.getConnection()` 得到 `Connection`。
3. **获取数据库操作对象**：通过 `conn.createStatement()` 得到 `Statement`。
4. **执行 SQL**：通过 `stmt.executeUpdate()` 执行 `UPDATE`。
5. **处理查询结果集**：本次执行的不是 `SELECT`，因此没有 `ResultSet`，跳过这一步。
6. **释放资源**：通过 try-with-resources 自动关闭 `Statement` 和 `Connection`。

因此，JDBC 六步的本质可以概括为：**先建立 Java 程序与数据库之间的连接，再通过数据库操作对象发送 SQL，根据 SQL 类型处理执行结果，最后及时释放数据库资源。**

## JDBC 驱动注册与连接配置

### 使用 `Class.forName()` 加载驱动

前面注册 MySQL JDBC 驱动时，可以显式创建驱动对象并调用 `DriverManager.registerDriver()`：

```java
Driver driver = new com.mysql.cj.jdbc.Driver();
DriverManager.registerDriver(driver);
```

这种方式直接体现了 JDBC 驱动注册的底层过程：先创建 MySQL 提供的 `Driver` 实现对象，再将其注册到 `DriverManager` 中。

传统 JDBC 开发中还经常采用另一种更加简洁的方式：

```java
Class.forName("com.mysql.cj.jdbc.Driver");
```

与显式创建驱动对象相比，`Class.forName()` 有两个主要特点：

1. 代码更加简洁，不需要程序员直接创建驱动对象并调用 `registerDriver()`。
2. `Class.forName()` 接收的是类的**全限定类名字符串**，因此可以把驱动类名放入配置文件，而不必直接写死在 Java 源代码中。

例如，可以将 `com.mysql.cj.jdbc.Driver` 写入属性配置文件，Java 程序读取配置后再执行 `Class.forName(driver)`。这种方式可以进一步降低程序与具体数据库驱动之间的耦合。相关代码也体现了这一点：`Class.forName()` 的返回值并不需要使用，因为这里真正需要的是**触发驱动类的加载过程**。

#### `Class.forName()` 为什么能够完成驱动注册

`Class.forName("com.mysql.cj.jdbc.Driver")` 本身并没有直接调用 `DriverManager.registerDriver()`。它能够完成驱动注册，与 MySQL 驱动类自身的实现有关。

MySQL 驱动类中包含类似下面的静态代码块：

```java
static {
    try {
        DriverManager.registerDriver(new Driver());
    } catch (SQLException e) {
        throw new RuntimeException("Can't register driver!");
    }
}
```

当 JVM 第一次主动加载 `com.mysql.cj.jdbc.Driver` 类时，会执行该类的静态代码块，而静态代码块内部又调用了 `DriverManager.registerDriver()`，因此最终完成驱动注册。

整个过程可以理解为：

```text
Class.forName("com.mysql.cj.jdbc.Driver")
                ↓
       加载并初始化 Driver 类
                ↓
          执行静态代码块
                ↓
DriverManager.registerDriver(new Driver())
                ↓
            完成驱动注册
```

因此：

**`Class.forName()` 并不是 JDBC 专门提供的注册驱动方法，它只是触发了驱动类的加载和初始化，而真正的注册操作仍然由驱动类内部完成。**

> **注意**
>
> `Class.forName()` 可能抛出 `ClassNotFoundException`。如果驱动 JAR 没有正确加入 Classpath，JVM 无法找到 `com.mysql.cj.jdbc.Driver`，就会出现该异常。

------

### JDBC 4.0 之后的驱动自动注册

`Class.forName()` 是传统 JDBC 程序中非常常见的驱动加载方式，但从 **JDBC 4.0（Java 6）**开始，符合 JDBC 4.0 规范的驱动通常可以被系统自动发现和加载。

因此，在驱动 JAR 已经正确加入 Classpath 的情况下，现代 JDBC 程序通常可以省略：

```java
Class.forName("com.mysql.cj.jdbc.Driver");
```

直接获取数据库连接：

```java
Connection conn =
        DriverManager.getConnection(url, user, password);
```

也就是说，传统 JDBC 六步中的“注册驱动”在概念上仍然存在，但在代码层面通常不再需要程序员显式完成。

例如，即使将 `Class.forName("com.mysql.cj.jdbc.Driver")` 注释掉，程序仍然可以直接通过 `DriverManager.getConnection()` 获取连接并执行 SQL。

因此需要区分两个角度：

| 场景                             | 是否通常需要显式加载驱动                         |
| -------------------------------- | ------------------------------------------------ |
| 学习 JDBC 驱动注册原理           | 建议了解 `registerDriver()` 和 `Class.forName()` |
| 传统 JDBC 或旧项目               | 经常可以看到 `Class.forName()`                   |
| JDBC 4.0 之后的现代驱动          | 通常可以省略显式驱动加载                         |
| 不支持自动发现的旧驱动或特殊驱动 | 可能仍然需要手动加载                             |

> **结论**
>
> `Class.forName()` 是理解传统 JDBC 驱动注册机制的重要写法，但不应理解成现代 JDBC 程序必须执行的固定步骤。使用 JDBC 4.0 之后符合规范的驱动时，只要驱动已经正确加入 Classpath，通常可以由 JDBC 自动完成驱动发现和加载。

------

### 将数据库连接信息放入配置文件

如果数据库驱动、URL、用户名和密码全部直接写在 Java 源代码中：

```java
String url = "jdbc:mysql://localhost:3306/jdbc";
String user = "root";
String password = "123456";
```

一旦数据库地址、账号或者数据库类型发生变化，就需要修改 Java 源代码并重新编译程序。

为了降低这些容易变化的信息与 Java 程序之间的耦合，可以将其提取到属性配置文件中。

例如创建 `jdbc.properties`：

```properties
driver=com.mysql.cj.jdbc.Driver
url=jdbc:mysql://localhost:3306/jdbc
user=root
password=123456
```

这样可以将程序划分为两个部分：

- **Java 代码负责数据库操作逻辑**；
- **配置文件负责保存容易变化的数据库连接信息**。

当数据库连接信息发生变化时，只需要修改配置文件，Java 代码本身通常不需要调整。

这体现了开闭原则的思想：**尽量通过修改配置完成变化，而不是频繁修改已经编写完成的程序逻辑。**

------

### 使用 `ResourceBundle` 读取配置文件

对于 `.properties` 属性文件，可以使用 `ResourceBundle` 读取其中的配置。

假设存在 `jdbc.properties`：

```properties
driver=com.mysql.cj.jdbc.Driver
url=jdbc:mysql://localhost:3306/jdbc
user=root
password=123456
```

可以通过：

```java
ResourceBundle bundle = ResourceBundle.getBundle("jdbc");

String driver = bundle.getString("driver");
String url = bundle.getString("url");
String user = bundle.getString("user");
String password = bundle.getString("password");
```

获取配置。

其中：

```java
ResourceBundle.getBundle("jdbc");
```

指定的是资源文件的基本名称，因此这里对应的是 Classpath 下的 `jdbc.properties`，调用时不需要填写 `.properties` 后缀。

如果配置文件位于包目录中，则需要使用对应的包路径。例如代码中的 `ResourceBundle.getBundle("resources.jdbc")` 会读取相应路径中的 `jdbc.properties`。读取完成后，再通过 `getString("driver")`、`getString("url")` 等方法分别获取数据库连接信息。

读取配置后，JDBC 程序就可以写为：

```java
ResourceBundle bundle = ResourceBundle.getBundle("jdbc");

String driver = bundle.getString("driver");
String url = bundle.getString("url");
String user = bundle.getString("user");
String password = bundle.getString("password");

Class.forName(driver);

try (
        Connection conn =
                DriverManager.getConnection(url, user, password);

        Statement stmt =
                conn.createStatement()
) {
    // 执行数据库操作
}
```

这里最重要的变化是：

```text
原来：
Java 源代码 → 直接写死数据库连接信息

现在：
Java 源代码 → 读取配置文件 → 获取数据库连接信息
```

这样即使以后修改 `url`、`user`、`password`，甚至传统项目中需要修改 `driver`，数据库操作代码也可以保持不变。

## JDBC 工具类的封装

### 为什么需要封装工具类

随着 JDBC 程序逐渐增多，会发现很多代码会反复出现，例如：

- 读取数据库连接配置；
- 加载 JDBC 驱动；
- 获取 `Connection`；
- 关闭 `ResultSet`、`Statement` 和 `Connection`。

如果每一个 DAO 或测试类都重复编写这些代码，不仅代码量较大，而且一旦数据库配置读取方式发生变化，需要同时修改很多地方。

因此，可以将这些重复操作封装到一个 JDBC 工具类中，例如 `DbUtils` 或 `DBUtil`。

工具类负责处理公共 JDBC 操作，业务代码只需要调用工具类提供的方法。

例如：

```text
业务代码
   ↓
DbUtils.getConnection()
   ↓
获取 Connection
   ↓
执行自己的 SQL
```

实际使用工具类后，业务程序可以直接通过 `DBUtil.getConnection()` 获取连接，而不再关心 URL、用户名和密码等连接细节。

------

### `DbUtils` 的基本设计

一个基础 JDBC 工具类通常可以封装以下内容：

1. 在类加载时读取数据库配置。
2. 必要时完成驱动加载。
3. 提供统一的 `getConnection()` 方法。
4. 对传统 JDBC 写法，可以提供统一的资源关闭方法。

例如：

```java
import java.sql.*;
import java.util.ResourceBundle;

public class DbUtils {

    private static final String URL;
    private static final String USER;
    private static final String PASSWORD;

    static {
        ResourceBundle bundle =
                ResourceBundle.getBundle("jdbc");

        String driver = bundle.getString("driver");
        URL = bundle.getString("url");
        USER = bundle.getString("user");
        PASSWORD = bundle.getString("password");

        try {
            Class.forName(driver);
        } catch (ClassNotFoundException e) {
            throw new RuntimeException(e);
        }
    }

    public static Connection getConnection()
            throws SQLException {

        return DriverManager.getConnection(
                URL, USER, PASSWORD
        );
    }

    public static void close(
            Connection conn,
            Statement stmt,
            ResultSet rs) {

        if (rs != null) {
            try {
                rs.close();
            } catch (SQLException e) {
                e.printStackTrace();
            }
        }

        if (stmt != null) {
            try {
                stmt.close();
            } catch (SQLException e) {
                e.printStackTrace();
            }
        }

        if (conn != null) {
            try {
                conn.close();
            } catch (SQLException e) {
                e.printStackTrace();
            }
        }
    }
}
```

#### 静态代码块的作用

数据库的 `driver`、`url`、`user` 和 `password` 属于整个工具类都需要使用的公共配置，没有必要在每次调用 `getConnection()` 时重新读取。

因此可以在静态代码块中完成初始化：

```java
static {
    // 读取配置
    // 加载驱动
}
```

静态代码块会在类初始化阶段执行，因此这些配置通常只需要初始化一次。

这种设计使 `getConnection()` 本身非常简单：

```java
public static Connection getConnection()
        throws SQLException {

    return DriverManager.getConnection(
            URL, USER, PASSWORD
    );
}
```

调用者不再需要知道具体的 `url`、`user` 和 `password`：

```java
Connection conn = DbUtils.getConnection();
```

------

### 工具类封装后的效果

没有工具类时，每个 JDBC 程序都可能需要重复编写：

```text
读取配置
   ↓
加载驱动
   ↓
DriverManager.getConnection(...)
   ↓
执行 SQL
   ↓
关闭资源
```

封装工具类以后：

```text
DbUtils.getConnection()
        ↓
   获得 Connection
        ↓
     执行 SQL
```

数据库配置和连接建立逻辑都被隐藏在 `DbUtils` 内部。

例如：

```java
try (
        Connection conn = DbUtils.getConnection();
        Statement stmt = conn.createStatement()
) {
    String sql =
            "delete from t_user where id = 3";

    int count = stmt.executeUpdate(sql);

    System.out.println(
            count == 1 ? "删除成功" : "删除失败"
    );
}
```

这种结构比每个类都重复编写 JDBC 初始化代码更加简洁。

> **补充**
>
> 如果已经使用 try-with-resources，通常可以直接让 `Connection`、`Statement`、`ResultSet` 自动关闭，此时工具类中的 `close()` 方法就不再是必需的。因此可以把工具类的核心职责进一步集中在**读取配置和获取数据库连接**上。

------

## `DriverManager.getConnection()` 的其他使用方式

`DriverManager` 提供了多种获取数据库连接的重载方法，常见的有以下三种：

| 方法                                 | 连接信息的提供方式              |
| ------------------------------------ | ------------------------------- |
| `getConnection(url, user, password)` | URL、用户名、密码分别传入       |
| `getConnection(url)`                 | 用户名、密码等信息包含在 URL 中 |
| `getConnection(url, properties)`     | URL 与其他连接属性分开传入      |

代码中也可以看到这三种基本使用形式。

其中最容易理解、也最常见的是：

```java
Connection conn =
        DriverManager.getConnection(
                url, user, password
        );
```

另外两种方式作为了解即可。

------

### `getConnection(String url)`

`getConnection(String url)` 只有一个参数，因此用户名和密码等连接属性需要包含在 JDBC URL 中。

例如：

```java
String url =
        "jdbc:mysql://localhost:3306/jdbc?user=root&password=123456";

Connection conn =
        DriverManager.getConnection(url);
```

这里通过 URL 参数：

`user=root` 和 `password=123456`

提供数据库用户名和密码。

多个参数之间使用 `&` 连接，因此还可以继续增加其他连接属性，例如：

```text
jdbc:mysql://localhost:3306/jdbc?user=root&password=123456&useSSL=false
```

这种写法可以建立数据库连接，但 URL 会逐渐变长，并且用户名、密码与其他连接属性全部混合在同一个字符串中，因此一般只需要知道 JDBC 支持这种写法即可。

------

### `getConnection(String url, Properties info)`

另一种方式是：

```java
DriverManager.getConnection(url, info);
```

第二个参数是一个 `Properties` 对象，可以将用户名、密码以及其他连接属性统一保存在其中。

例如：

```java
String url =
        "jdbc:mysql://localhost:3306/jdbc";

Properties info = new Properties();

info.setProperty("user", "root");
info.setProperty("password", "123456");
info.setProperty("useSSL", "false");
info.setProperty("serverTimezone", "Asia/Shanghai");

Connection conn =
        DriverManager.getConnection(url, info);
```

这种方式将：

**数据库地址**

和：

**用户名、密码、连接参数**

进行了分离。

例如实际代码中，可以将 `user`、`password`、`useUnicode`、`characterEncoding`、`useSSL`、`serverTimezone` 等属性放入 `Properties`，然后整体传递给 `DriverManager.getConnection(url, prop)`。

这些连接属性中的很多参数也可以直接写在 JDBC URL 后面，因此两种写法本质上都是**向 JDBC 驱动提供建立连接所需要的属性**，只是组织形式不同。

> **结论**
>
> `DriverManager.getConnection()` 的三种形式只是数据库连接信息的组织方式不同：
>
> - `getConnection(url, user, password)`：连接信息分别传递，最直观；
> - `getConnection(url)`：连接属性全部放入 JDBC URL；
> - `getConnection(url, properties)`：使用 `Properties` 集中保存其他连接属性。
>
> 当前阶段重点掌握 `getConnection(url, user, password)` 即可，另外两种方式了解其使用形式和基本原理即可。

------

## JDBC 配置与连接流程总结

随着 JDBC 代码逐步完善，数据库连接方式可以从最初的硬编码逐渐演变为：

```text
jdbc.properties
      ↓
读取 driver、url、user、password
      ↓
必要时加载 JDBC Driver
      ↓
DbUtils.getConnection()
      ↓
DriverManager.getConnection(...)
      ↓
Connection
      ↓
执行数据库操作
```

这一过程体现了 JDBC 程序逐步降低耦合的思路：

1. 最初直接在 Java 代码中创建具体驱动对象。
2. 使用 `Class.forName()` 后，不再直接依赖驱动实现类对象。
3. 将驱动类名和数据库连接信息放入配置文件，使连接信息与 Java 源代码分离。
4. 将配置读取和连接获取等重复逻辑封装到工具类中，使业务代码只关注具体数据库操作。
5. JDBC 4.0 之后，对于支持自动发现的驱动，通常还可以进一步省略显式的驱动加载代码。

因此，这一阶段 JDBC 代码优化的核心不是改变数据库操作本身，而是逐步做到：**将容易变化的配置从代码中抽离，将重复的 JDBC 基础操作集中封装，使业务代码与数据库连接细节之间的耦合越来越低。**

## JDBC 查询操作

### `ResultSet` 查询结果集

执行 `SELECT` 查询后，JDBC 会使用 `ResultSet` 对查询结果进行封装。`ResultSet` 是 `java.sql` 包中的接口，其中保存了查询结果中的多行数据，可以通过移动游标的方式逐行读取。

查询操作通常使用 `Statement.executeQuery()`：

```java
String sql =
        "select id, name, password, realname, gender, tel from t_user";

ResultSet rs = stmt.executeQuery(sql);
```

与数据修改操作不同，`INSERT`、`DELETE`、`UPDATE` 通常使用 `executeUpdate()` 并返回影响记录数，而 `SELECT` 使用 `executeQuery()` 并返回 `ResultSet`。

| SQL 类型                     | 常用方法          | 返回结果                    |
| ---------------------------- | ----------------- | --------------------------- |
| `INSERT`、`DELETE`、`UPDATE` | `executeUpdate()` | `int`，表示影响的记录条数   |
| `SELECT`                     | `executeQuery()`  | `ResultSet`，表示查询结果集 |

查询得到 `ResultSet` 后，需要通过 `next()` 移动游标，再使用 `getXXX()` 系列方法读取当前行的数据。实际查询代码也采用了 `executeQuery()` 获取结果集，然后循环调用 `next()` 读取数据。

------

### `ResultSet` 的游标与遍历

`ResultSet` 内部可以理解为存在一个指向当前数据行的**游标（cursor）**。结果集刚创建时，游标并没有指向第一条数据，而是位于第一条记录之前，因此必须先调用一次 `next()` 才能读取第一行。

`next()` 的作用是：

1. 将游标向下一行移动。
2. 如果移动后指向有效数据行，则返回 `true`。
3. 如果已经没有下一行，则返回 `false`。

因此，遍历结果集通常使用：

```java
while (rs.next()) {
    // 读取并处理当前行
}
```

整个过程可以表示为：

```text
初始位置：第一行之前
        ↓ next()
      第一行
        ↓ next()
      第二行
        ↓ next()
       ...
        ↓ next()
     结果集末尾
        ↓
      返回 false
```

每进入一次 `while` 循环体，处理的都是**当前游标所指向的一整行数据**。

例如：

```java
while (rs.next()) {
    String id = rs.getString("id");
    String name = rs.getString("name");

    System.out.println(id + "\t" + name);
}
```

这里第一次执行 `rs.next()` 后游标指向第一行，然后读取第一行的 `id` 和 `name`；再次执行 `rs.next()` 后，游标移动到第二行，如此反复，直到没有更多数据。

> **易错点**
>
> 不能在刚获得 `ResultSet` 后直接读取列值。此时游标还没有指向任何有效数据行，必须先执行 `next()`。

------

### 通过列索引获取数据

读取当前行中的某一列，可以通过**列索引**进行定位。

例如 SQL：

```sql
SELECT id, name, password, realname, gender, tel
FROM t_user;
```

查询结果中的列顺序为：

| 列索引 | 查询结果列 |
| ------ | ---------- |
| `1`    | `id`       |
| `2`    | `name`     |
| `3`    | `password` |
| `4`    | `realname` |
| `5`    | `gender`   |
| `6`    | `tel`      |

因此可以按照列的位置读取：

```java
while (rs.next()) {
    String id = rs.getString(1);
    String name = rs.getString(2);
    String password = rs.getString(3);
    String realname = rs.getString(4);
    String gender = rs.getString(5);
    String tel = rs.getString(6);

    System.out.println(
            id + "\t" +
            name + "\t" +
            password + "\t" +
            realname + "\t" +
            gender + "\t" +
            tel
    );
}
```

JDBC 中结果集的列索引**从 `1` 开始，而不是从 `0` 开始**。代码中通过 `rs.getString(1)`、`rs.getString(2)` 等方式读取查询结果，并特别强调 JDBC 的列下标从 `1` 开始。

这里的索引是**查询结果中的列序号**，取决于 `SELECT` 后列的排列顺序。

例如：

```sql
SELECT name, id
FROM t_user;
```

此时 `rs.getString(1)` 读取的是 `name`，`rs.getString(2)` 才是 `id`。

因此，通过列索引获取数据虽然写法简单，但 SQL 中列的顺序一旦发生变化，Java 代码也可能需要同步修改。

------

### 通过列名获取数据

除了通过列索引，还可以按照查询结果中的**列名**读取数据。

例如：

```sql
SELECT id, name AS username, realname
FROM t_user;
```

可以写为：

```java
while (rs.next()) {
    String id = rs.getString("id");
    String username = rs.getString("username");
    String realname = rs.getString("realname");

    System.out.println(
            id + "\t" +
            username + "\t" +
            realname
    );
}
```

相比列索引，列名能够直接体现读取的是哪一列，因此通常具有更好的可读性。实际查询代码同样演示了通过 `empno`、`ename` 和别名 `salary` 获取数据。

需要特别注意的是：

**`ResultSet` 按列名读取数据时，使用的是查询结果中的列名称，而不是一定使用数据库表中原始字段的名称。**

例如：

```sql
SELECT id, name AS username
FROM t_user;
```

查询结果中的第二列名称已经变成 `username`，因此应该写：

```java
String name = rs.getString("username");
```

而不是：

```java
String name = rs.getString("name");
```

同样，如果查询：

```sql
SELECT empno, ename, sal AS salary
FROM emp;
```

则应使用 `salary` 获取该列：

```java
double salary = rs.getDouble("salary");
```

代码中也明确将 `sal` 起别名为 `salary`，之后通过 `rs.getString("salary")` 获取查询结果。

> **易错点**
>
> 使用列名读取数据时，应以**查询结果中的列名或别名**为准。SQL 中如果通过 `AS` 修改了列名，后续通常应按照别名读取。

------

### 使用 `getXXX()` 获取指定类型的数据

`ResultSet` 提供了一系列 `getXXX()` 方法，可以按照需要将当前列读取为对应的 Java 类型。

常见方法包括：

| 方法          | 常见返回类型    |
| ------------- | --------------- |
| `getString()` | `String`        |
| `getInt()`    | `int`           |
| `getLong()`   | `long`          |
| `getDouble()` | `double`        |
| `getDate()`   | `java.sql.Date` |

例如查询商品信息：

```sql
SELECT id, name, price, create_time AS createTime
FROM t_product;
```

可以根据各列需要的类型分别获取：

```java
while (rs.next()) {
    long id = rs.getLong("id");
    String name = rs.getString("name");
    double price = rs.getDouble("price");
    java.sql.Date createTime =
            rs.getDate("createTime");

    System.out.println(
            id + "\t" +
            name + "\t" +
            price + "\t" +
            createTime
    );
}
```

使用指定类型读取后，得到的数据可以直接参与对应类型的运算。例如：

```java
double price = rs.getDouble("price");

System.out.println(price * 2);
```

实际查询代码也分别使用 `getInt()`、`getString()` 和 `getDouble()` 读取不同列，并直接对读取到的工资数据进行数值运算。

如果使用 `getString()`，则可以将查询列以字符串形式读取。例如：

```java
String id = rs.getString("id");
String price = rs.getString("price");
```

因此，实际开发中应根据数据后续的用途选择合适的 `getXXX()` 方法，而不是所有数据都统一使用 `String`。

------

### `ResultSet` 的资源释放

`ResultSet` 也是 JDBC 资源，使用完成后需要及时关闭。

查询操作通常涉及三个主要资源，其创建顺序为：

```text
Connection
    ↓
Statement
    ↓
ResultSet
```

释放时按照相反顺序关闭：

```text
ResultSet
    ↓
Statement
    ↓
Connection
```

传统写法为：

```java
if (rs != null) {
    try {
        rs.close();
    } catch (SQLException e) {
        e.printStackTrace();
    }
}

if (stmt != null) {
    try {
        stmt.close();
    } catch (SQLException e) {
        e.printStackTrace();
    }
}

if (conn != null) {
    try {
        conn.close();
    } catch (SQLException e) {
        e.printStackTrace();
    }
}
```

如果使用 try-with-resources，可以将三个资源统一声明在资源区域中：

```java
String sql =
        "select empno, ename, sal as salary from emp";

try (
        Connection conn = DBUtil.getConnection();
        Statement stmt = conn.createStatement();
        ResultSet rs = stmt.executeQuery(sql)
) {

    while (rs.next()) {
        int empno = rs.getInt("empno");
        String ename = rs.getString("ename");
        double salary = rs.getDouble("salary");

        System.out.println(
                empno + "\t" +
                ename + "\t" +
                salary
        );
    }

} catch (SQLException e) {
    e.printStackTrace();
}
```

这种写法会在离开 `try` 时自动关闭相关 JDBC 资源，实际查询代码也直接将 `Connection`、`Statement` 和 `ResultSet` 都放入 try-with-resources 中管理。

------

## 查询结果集的元数据

### 什么是 `ResultSetMetaData`

`ResultSet` 保存的是查询得到的**具体数据**，而 `ResultSetMetaData` 保存的是查询结果集自身的**结构信息**。

所谓**元数据（Metadata）**，可以理解为“描述数据的数据”。

例如下面是一组查询结果：

| empno | ename | salary |
| ----- | ----- | ------ |
| 7369  | SMITH | 800    |
| 7499  | ALLEN | 1600   |

其中 `7369`、`SMITH`、`800` 属于具体的数据，而以下内容属于结果集的元数据：

- 查询结果共有多少列；
- 第一列叫什么；
- 第二列的数据类型是什么；
- 某一列的显示长度是多少；
- 查询结果中某列使用了什么别名。

因此：

**`ResultSet` 用于读取数据本身，`ResultSetMetaData` 用于描述查询结果的结构。**

------

### 获取 `ResultSetMetaData`

可以通过 `ResultSet.getMetaData()` 获取结果集对应的元数据对象：

```java
ResultSetMetaData rsmd = rs.getMetaData();
```

代码中也是先得到 `ResultSet`，再通过 `rs.getMetaData()` 获取 `ResultSetMetaData`。

常用方法包括：

| 方法                        | 作用                               |
| --------------------------- | ---------------------------------- |
| `getColumnCount()`          | 获取查询结果的列数                 |
| `getColumnName(int)`        | 获取指定列的名称                   |
| `getColumnLabel(int)`       | 获取指定列在查询结果中的标签或别名 |
| `getColumnType(int)`        | 获取列对应的 SQL 类型编号          |
| `getColumnTypeName(int)`    | 获取列对应的数据库类型名称         |
| `getColumnDisplaySize(int)` | 获取列的显示宽度                   |

例如：

```java
ResultSetMetaData rsmd = rs.getMetaData();

int columnCount = rsmd.getColumnCount();

for (int i = 1; i <= columnCount; i++) {
    String columnName =
            rsmd.getColumnName(i);

    String columnType =
            rsmd.getColumnTypeName(i);

    System.out.println(
            "列名：" + columnName +
            "，类型：" + columnType
    );
}
```

元数据中的列编号同样**从 `1` 开始**，因此遍历通常写为 `i = 1; i <= columnCount; i++`。实际代码也是按照这一方式遍历全部列。

------

### `getColumnName()` 与 `getColumnLabel()`

在查询结果存在列别名时，需要区分列原始名称和查询结果中的标签。

例如：

```sql
SELECT empno, ename, sal AS salary
FROM emp;
```

其中数据库中的原始字段名称是 `sal`，而查询结果中使用的别名是 `salary`。

可以分别通过：

```java
rsmd.getColumnName(i);
rsmd.getColumnLabel(i);
```

获取相关信息。代码中同时演示了 `getColumnName()` 和 `getColumnLabel()`，其中 `getColumnLabel()` 用于取得查询结果中的列标签。

`ResultSetMetaData` 的典型用途是：**在程序事先不知道查询结果包含哪些列时，动态获取结果集的结构信息。**

当前阶段将其作为了解内容即可，重点掌握 `ResultSet` 的遍历和取值。

------

## 获取新增记录的主键值

### 为什么需要获取新增主键

很多数据库表的主键采用自增方式生成。例如插入用户时，只提供用户名、密码等业务数据：

```sql
INSERT INTO tb_user(username, password, real_name)
VALUES ('zhangsan', '123456', '张三');
```

主键 `id` 由数据库自动生成。

某些业务场景中，插入完成之后还需要立即使用刚刚生成的主键。例如：

```text
新增订单
   ↓
数据库生成 order_id
   ↓
继续插入订单明细
   ↓
订单明细需要使用刚生成的 order_id
```

此时就需要 JDBC 在执行 `INSERT` 后取得数据库生成的主键值。

------

### 指定返回自动生成的主键

普通新增操作通常写为：

```java
int count = stmt.executeUpdate(sql);
```

如果还需要获取数据库自动生成的主键，则可以调用 `executeUpdate()` 的重载形式，并传入：

```
Statement.RETURN_GENERATED_KEYS
```

例如：

```java
int count = stmt.executeUpdate(
        sql,
        Statement.RETURN_GENERATED_KEYS
);
```

该参数表示：**执行 SQL 的同时，要求 JDBC 保留数据库生成的键值，以便后续获取。**

实际代码中也是通过给 `executeUpdate()` 增加 `Statement.RETURN_GENERATED_KEYS` 参数来请求返回新增记录生成的主键。

------

### 通过 `getGeneratedKeys()` 获取主键

执行新增 SQL 后，再调用：

```java
ResultSet rs = stmt.getGeneratedKeys();
```

得到保存自动生成键值的 `ResultSet`。

然后仍然按照普通结果集的方式读取：

```java
if (rs.next()) {
    long id = rs.getLong(1);

    System.out.println(
            "新增记录的主键值：" + id
    );
}
```

整个过程可以概括为：

```text
执行 INSERT
    ↓
指定 RETURN_GENERATED_KEYS
    ↓
数据库生成主键
    ↓
stmt.getGeneratedKeys()
    ↓
得到 ResultSet
    ↓
rs.next()
    ↓
读取生成的主键
```

完整的核心代码为：

```java
String sql =
        "insert into tb_user(" +
        "username, password, real_name, gender, phone" +
        ") values(" +
        "'zhangsan', '123456', '张三', '男', '16666666666'" +
        ")";

int count = stmt.executeUpdate(
        sql,
        Statement.RETURN_GENERATED_KEYS
);

ResultSet rs = stmt.getGeneratedKeys();

if (rs.next()) {
    long userId = rs.getLong(1);

    System.out.println(
            "新增记录的主键值：" + userId
    );
}
```

实际代码同样是在执行新增后调用 `stmt.getGeneratedKeys()`，随后通过 `rs.getLong(1)` 读取生成的主键。

这里的 `ResultSet` 与普通查询结果集在使用方式上相同：都需要先执行 `next()`，再读取当前行中的数据。

> **注意**
>
> `getGeneratedKeys()` 返回的也是 `ResultSet`，因此使用完成后同样需要及时关闭。不同数据库及其 JDBC 驱动对自动生成键值的具体支持方式可能存在差异，实际使用时需要结合所使用的数据库和驱动进行处理。

------

## JDBC 查询操作总结

JDBC 查询操作相比 `INSERT`、`DELETE`、`UPDATE` 多出的核心步骤，就是**处理 `ResultSet` 查询结果集**。

完整逻辑可以概括为：

```text
获取 Connection
       ↓
获取 Statement
       ↓
执行 executeQuery()
       ↓
获得 ResultSet
       ↓
通过 next() 逐行移动游标
       ↓
通过 getXXX() 获取当前行各列数据
       ↓
处理数据
       ↓
继续 next()
       ↓
直到结果集遍历结束
       ↓
释放 ResultSet、Statement、Connection
```

其中需要重点掌握以下规则：

1. `SELECT` 通常通过 `executeQuery()` 执行，并返回 `ResultSet`。
2. `ResultSet` 初始游标位于第一行之前，必须先调用 `next()`。
3. `next()` 返回 `true` 表示存在有效的当前行，返回 `false` 表示结果集已经遍历结束。
4. 可以通过列索引或列名读取数据，其中 JDBC 的列索引从 `1` 开始。
5. 使用列名读取时，应以**查询结果中的列名或别名**为准。
6. 可以根据需要使用 `getString()`、`getInt()`、`getLong()`、`getDouble()`、`getDate()` 等方法获取指定 Java 类型的数据。
7. `ResultSetMetaData` 用于描述结果集本身的列数、列名、数据类型等结构信息。
8. 新增数据后如果需要取得数据库自动生成的主键，可以使用 `Statement.RETURN_GENERATED_KEYS` 配合 `getGeneratedKeys()`。
9. `ResultSet` 属于 JDBC 资源，使用完成后需要及时释放；如果使用 try-with-resources，可以让 Java 自动完成资源关闭。

> **结论**
>
> JDBC 查询的核心可以记为：**`executeQuery()` 负责得到结果集，`next()` 负责逐行移动，`getXXX()` 负责读取当前行数据。** 掌握这三个环节，就掌握了最基础的 JDBC 查询结果处理方式。

## SQL 注入与 PreparedStatement

### SQL 注入问题

**SQL 注入（SQL Injection）是指程序将不可信的外部输入直接拼接到 SQL 语句中，导致输入内容被数据库当作 SQL 语法的一部分解析，从而改变原 SQL 的执行逻辑。**

以用户登录为例，程序通常希望执行类似下面的查询：

```sql
SELECT id
FROM tb_user
WHERE username = '用户输入的用户名'
  AND password = '用户输入的密码';
```

只有用户名和密码同时匹配时，查询结果才应该存在，程序据此判断登录成功。

如果使用字符串拼接构造 SQL：

```java
String sql =
        "select id from tb_user " +
        "where username = '" + username +
        "' and password = '" + password + "'";
```

那么用户输入的内容就会直接成为 SQL 文本的一部分。代码中的登录逻辑正是先将 `username`、`password` 与 SQL 字符串拼接，再通过 `Statement` 执行。

假设某个输入中包含额外的 SQL 逻辑，最终拼接出来的条件可能发生变化，例如：

```sql
SELECT id
FROM tb_user
WHERE username = 'aaa'
  AND password = 'bbb'
  OR '1' = '1';
```

由于 `'1' = '1'` 恒为真，整个 `WHERE` 条件可能因此成立。如果程序又采用“结果集中存在数据即登录成功”的判断方式，就可能绕过正常的身份验证。

SQL 注入发生的关键过程是：

```text
外部输入
   ↓
直接拼接到 SQL 字符串
   ↓
形成新的完整 SQL
   ↓
数据库统一解析其中的 SQL 结构和输入内容
   ↓
输入中的特殊内容可能改变原有 SQL 逻辑
```

源代码中也将问题概括为：用户输入含有 SQL 相关内容，并参与了后续 SQL 字符串的拼接和解析，最终使 SQL 原意发生变化。

> **易错点**
>
> SQL 注入的根本原因不能简单归结为“使用了 `Statement`”。真正的问题是：**将不可信数据直接拼接到 SQL 结构中。** `Statement` 本身仍然可以安全地执行不包含外部动态输入的固定 SQL；风险主要出现在使用字符串拼接构造动态 SQL 时。

------

### 使用 `PreparedStatement` 防止 SQL 注入

JDBC 提供了 `PreparedStatement` 接口，用于执行带参数的 SQL。`PreparedStatement` 是 `Statement` 的子接口，因此同样属于数据库操作对象，但它允许将**SQL 结构**和**参数值**分开处理。

例如登录查询可以写为：

```java
String sql =
        "select id from tb_user " +
        "where username = ? and password = ?";

PreparedStatement ps =
        conn.prepareStatement(sql);

ps.setString(1, username);
ps.setString(2, password);

ResultSet rs = ps.executeQuery();
```

这里的 `?` 是**参数占位符**。程序先确定 SQL 的整体结构，再通过 `setString()` 等方法向指定位置绑定参数。代码中也是使用两个 `?` 表示用户名和密码，并通过 `setString()` 分别赋值。

其核心区别可以理解为：

```text
Statement：

SQL 片段 + 用户数据
        ↓
字符串拼接
        ↓
完整 SQL
        ↓
数据库解析
```

而 `PreparedStatement` 是：

```text
带 ? 的 SQL 结构
        ↓
prepareStatement()
        ↓
绑定参数值
        ↓
执行 SQL
```

当使用正确的参数绑定方式时，即使参数值中包含引号、SQL 关键字或其他特殊字符，它们也会被作为**参数值本身**处理，而不会被当作 SQL 结构的一部分重新解释，因此能够有效防止这类 SQL 注入。

代码中的登录示例也明确通过 `PreparedStatement` 将参数值和 SQL 结构分离，从而避免输入数据参与 SQL 结构的构造。

> **结论**
>
> 防止 SQL 注入的核心不是“过滤几个危险关键字”，而是：**不要把不可信输入直接拼接进 SQL，应该使用 `PreparedStatement` 的参数绑定机制。**

------

### `PreparedStatement` 占位符的使用规则

带有 `?` 的 SQL 可以理解为**参数化 SQL**。例如：

```java
String sql =
        "select id from tb_user " +
        "where username = ? and password = ?";
```

使用占位符时需要掌握以下规则。

#### 占位符不能加引号

正确写法是：

```sql
WHERE username = ?
```

不能写成：

```sql
WHERE username = '?'
```

`?` 本身就是参数位置。如果将其写在单引号或双引号内部，它就会成为普通字符，而不再是 JDBC 参数占位符。源代码中也明确区分了 `?` 和 `'?'`：前者是参数位置，后者只是普通字符串内容。

#### 占位符编号从 `1` 开始

例如：

```java
ps.setString(1, username);
ps.setString(2, password);
```

其中第一个参数表示第几个 `?`：

- `1` 对应第一个 `?`；
- `2` 对应第二个 `?`；
- 后续依次递增。

JDBC 中这里的参数索引同样从 `1` 开始。

#### 每个占位符都需要绑定参数

例如 SQL 中存在三个占位符：

```java
String sql =
        "update emp " +
        "set ename = ?, job = ? " +
        "where empno = ?";
```

就应分别绑定三个值：

```java
ps.setString(1, "李四");
ps.setString(2, "产品经理");
ps.setInt(3, 8888);
```

如果遗漏必要参数，执行 SQL 时通常会产生异常。

#### 根据数据类型选择 `setXXX()`

`PreparedStatement` 提供了多种参数绑定方法：

| 方法          | 常见用途      |
| ------------- | ------------- |
| `setString()` | 字符串        |
| `setInt()`    | `int` 整数    |
| `setLong()`   | `long` 整数   |
| `setDouble()` | `double` 数值 |
| `setDate()`   | SQL 日期      |
| `setBlob()`   | 二进制大对象  |
| `setObject()` | 通用对象绑定  |

例如：

```java
ps.setInt(1, 1001);
ps.setString(2, "张三");
ps.setDouble(3, 5000.0);
```

这样不仅避免字符串拼接，也能够更加明确地表达参数的数据类型。

------

### `Statement` 与 `PreparedStatement`

二者都是 JDBC 中用于执行 SQL 的接口，其中 `PreparedStatement` 继承自 `Statement`。源代码中也明确体现了二者的继承关系及参数化执行的基本区别。

| 对比项       | `Statement`                  | `PreparedStatement`                     |
| ------------ | ---------------------------- | --------------------------------------- |
| SQL 参数     | 通常通过字符串构造完整 SQL   | 使用 `?` 占位并绑定参数                 |
| SQL 注入风险 | 动态字符串拼接时风险较高     | 正确参数绑定时可有效防止注入            |
| 类型处理     | 动态值通常需要自行拼入 SQL   | 可通过 `setInt()`、`setString()` 等绑定 |
| 可读性       | 动态参数较多时容易混乱       | SQL 结构与参数明显分离                  |
| 适用场景     | 固定、不带外部参数的简单 SQL | 绝大多数带动态参数的 SQL                |

`PreparedStatement` 还有可能带来 SQL 执行效率方面的优势，但实际是否发生服务器端预编译、是否复用执行计划以及如何缓存，取决于**数据库、JDBC 驱动和具体配置**。

因此，不宜简单死记为：

**“`PreparedStatement` 一定只编译一次，以后永远不再编译。”**

当前阶段更重要的是掌握它的两个核心价值：

**参数化 SQL，防止 SQL 注入；参数与 SQL 结构分离，使代码更加清晰、类型更加明确。**

> **结论**
>
> 实际 JDBC 开发中，只要 SQL 中包含动态数据，通常优先使用 `PreparedStatement`，而不是通过字符串拼接配合 `Statement`。

------

## PreparedStatement 的基本使用

### 新增数据

执行 `INSERT` 时，可以把所有动态值替换为 `?`：

```java
String sql =
        "insert into emp(" +
        "empno, ename, job, mgr, hiredate, sal, comm, deptno" +
        ") values (?, ?, ?, ?, ?, ?, ?, ?)";

try (
        Connection conn = DBUtil.getConnection();
        PreparedStatement ps =
                conn.prepareStatement(sql)
) {
    ps.setInt(1, 8888);
    ps.setString(2, "李四");
    ps.setString(3, "办事员");
    ps.setInt(4, 7369);
    ps.setString(5, "2000-10-11");
    ps.setDouble(6, 10000.0);
    ps.setDouble(7, 300.0);
    ps.setInt(8, 40);

    int count = ps.executeUpdate();

    System.out.println(
            count == 1 ? "新增成功" : "新增失败"
    );
}
```

实际代码同样定义了 8 个占位符，并依次通过 `setInt()`、`setString()`、`setDouble()` 等方法完成参数绑定。

这里需要注意，使用 `PreparedStatement` 后，执行时通常调用：

```java
ps.executeUpdate();
```

而不是重新传入：

```java
ps.executeUpdate(sql);
```

因为 SQL 在创建 `PreparedStatement` 时已经提供：

```java
conn.prepareStatement(sql);
```

后续只需要绑定参数并执行。

------

### 修改数据

执行 `UPDATE` 的方式完全相同，只需要在动态位置设置占位符。

例如：

```java
String sql =
        "update dept " +
        "set loc = ?, dname = ? " +
        "where deptno = ?";

try (
        Connection conn = DBUtil.getConnection();
        PreparedStatement ps =
                conn.prepareStatement(sql)
) {
    ps.setString(1, "芝加哥");
    ps.setString(2, "销售部");
    ps.setInt(3, 30);

    int count = ps.executeUpdate();
}
```

这里三个 `?` 按照 SQL 中从左到右的顺序编号为 `1`、`2`、`3`。源代码中的修改操作也采用同样的参数绑定方式。

------

### 删除数据

删除操作的动态条件同样可以使用占位符：

```java
String sql =
        "delete from emp where empno = ?";

try (
        Connection conn = DBUtil.getConnection();
        PreparedStatement ps =
                conn.prepareStatement(sql)
) {
    ps.setInt(1, 8888);

    int count = ps.executeUpdate();
}
```

实际删除示例就是通过一个 `?` 接收员工编号，然后调用 `executeUpdate()` 完成删除。

因此，无论 `INSERT`、`UPDATE` 还是 `DELETE`，基本模式都相同：

```text
编写带 ? 的 SQL
      ↓
prepareStatement(sql)
      ↓
setXXX() 绑定参数
      ↓
executeUpdate()
```

## PreparedStatement 查询

### 普通查询

执行 `SELECT` 时，同样可以将查询条件参数化：

```java
String sql =
        "select id, username " +
        "from tb_user where id = ?";

try (
        Connection conn = DBUtil.getConnection();
        PreparedStatement ps =
                conn.prepareStatement(sql)
) {
    ps.setInt(1, 10);

    try (ResultSet rs = ps.executeQuery()) {
        while (rs.next()) {
            // 处理结果
        }
    }
}
```

查询时使用 `executeQuery()`，返回值仍然是 `ResultSet`，后续处理方式与前面学习的 JDBC 查询完全一致。

------

### 模糊查询

使用 `LIKE` 时，占位符仍然必须保持为独立的参数位置。

例如查询**第二个字符为 `O`**的员工姓名，对应模式为 `_O%`：

- `_` 表示任意一个字符；
- `O` 表示第二个字符必须为 `O`；
- `%` 表示后面可以存在任意数量的字符。

一种简单写法是：

```java
String sql =
        "select ename from emp where ename like ?";

PreparedStatement ps =
        conn.prepareStatement(sql);

ps.setString(1, "_O%");
```

这样整个模糊匹配模式 `_O%` 都作为参数值传入。

也可以在 SQL 中拼接模式：

```java
String sql =
        "select ename from emp " +
        "where ename like concat('_', ?, '%')";

PreparedStatement ps =
        conn.prepareStatement(sql);

ps.setString(1, "O");
```

实际代码采用的就是后一种方式。

错误写法是：

```java
String sql =
        "select ename from emp " +
        "where ename like '_?%'";
```

此时 `?` 位于单引号内部，已经变成普通字符串中的问号，不再是 JDBC 占位符。源代码同样明确将这种写法标记为错误。

> **易错点**
>
> 不要为了给参数添加 `%` 或 `_`，把 `?` 直接写进 SQL 字符串常量内部。可以选择把完整模式作为参数传入，例如 `ps.setString(1, "_O%")`，也可以使用数据库字符串函数组合模式。

------

### 分页查询

MySQL 可以通过 `LIMIT` 实现分页。

常见形式为：

```sql
LIMIT 起始下标, 每页记录数
```

假设每页显示 `pageSize` 条数据，第 `pageNo` 页的起始位置为：

```
(pageNo - 1) * pageSize
```

例如 `pageSize = 3`：

| 页码    | 起始位置 | SQL          |
| ------- | -------- | ------------ |
| 第 1 页 | `0`      | `LIMIT 0, 3` |
| 第 2 页 | `3`      | `LIMIT 3, 3` |
| 第 3 页 | `6`      | `LIMIT 6, 3` |

因此可以写为：

```java
int pageSize = 3;
int pageNo = 2;

int startIndex =
        (pageNo - 1) * pageSize;

String sql =
        "select ename from emp limit ?, ?";

PreparedStatement ps =
        conn.prepareStatement(sql);

ps.setInt(1, startIndex);
ps.setInt(2, pageSize);
```

代码中也是先根据 `pageSize * (pageNo - 1)` 计算起始位置，再将起始位置和每页条数分别绑定到两个占位符。

因此 MySQL 基础分页公式可以记为：

**起始位置 = `(pageNo - 1) \* pageSize`**

其中：

- `pageNo` 表示页码；
- `pageSize` 表示每页显示多少条数据。

> **注意**
>
> 数据库中的记录本身没有天然、稳定的显示顺序。真正进行分页查询时，通常应该结合明确的 `ORDER BY`，否则不同查询之间的分页结果顺序可能不稳定。

## BLOB 数据的存取

### 什么是 BLOB

**BLOB（Binary Large Object，二进制大对象）用于保存较大的二进制数据**，例如图片、音频或其他二进制文件。

例如可以创建一张用于保存图片的表：

```sql
CREATE TABLE t_img (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    img MEDIUMBLOB,
    PRIMARY KEY (id)
);
```

其中 `UNSIGNED` 表示该整数类型不包含负数；`MEDIUMBLOB` 用于保存二进制数据。

在 JDBC 中，处理 BLOB 数据时通常不会把整个文件内容拼接进 SQL，而是通过 `PreparedStatement` 配合输入流或 `Blob` 相关 API 进行处理。

------

### 向数据库写入 BLOB

写入图片时，可以先创建文件输入流：

```java
FileInputStream in =
        new FileInputStream("D:\\images\\photo.jpg");
```

然后使用：

```java
ps.setBlob(1, in);
```

将文件流绑定到 `BLOB` 参数。

完整核心逻辑为：

```java
String sql =
        "insert into t_img(img) values(?)";

try (
        Connection conn = DBUtil.getConnection();
        PreparedStatement ps =
                conn.prepareStatement(sql);

        FileInputStream in =
                new FileInputStream(
                        "D:\\images\\photo.jpg"
                )
) {
    ps.setBlob(1, in);

    int count = ps.executeUpdate();

    System.out.println(
            count == 1
                    ? "图片保存成功"
                    : "图片保存失败"
    );
}
```

实际代码同样通过 `FileInputStream` 读取硬盘文件，再使用 `ps.setBlob(1, in)` 将图片数据写入数据库。

整个过程可以理解为：

```text
本地图片文件
     ↓
FileInputStream
     ↓
setBlob()
     ↓
PreparedStatement
     ↓
数据库 BLOB 字段
```

由于 `FileInputStream` 也是需要关闭的资源，因此同样适合使用 try-with-resources 管理。

------

### 从数据库读取 BLOB

读取 BLOB 时，整体方向与写入相反：

```text
数据库 BLOB 字段
      ↓
ResultSet
      ↓
二进制输入流
      ↓
输出流
      ↓
本地文件
```

例如：

```java
String sql =
        "select img from t_img where id = ?";

try (
        Connection conn = DBUtil.getConnection();
        PreparedStatement ps =
                conn.prepareStatement(sql)
) {
    ps.setInt(1, 1);

    try (ResultSet rs = ps.executeQuery()) {

        if (rs.next()) {

            try (
                    InputStream in =
                            rs.getBinaryStream("img");

                    OutputStream out =
                            new FileOutputStream(
                                    "D:\\images\\copy.jpg"
                            )
            ) {
                byte[] bytes = new byte[1024];
                int readCount;

                while ((readCount =
                        in.read(bytes)) != -1) {

                    out.write(
                            bytes,
                            0,
                            readCount
                    );
                }
            }
        }
    }
}
```

实际代码也是通过 `ResultSet` 获取 `img` 列的二进制输入流，再使用文件输出流将数据逐块写回硬盘。

这里仍然采用标准的 IO 流处理方式：

1. 从数据库获得输入流；
2. 创建本地文件输出流；
3. 使用字节数组作为缓冲区；
4. 循环读取；
5. 每读取一部分就写入本地文件；
6. 最终关闭相关流和 JDBC 资源。

> **结论**
>
> BLOB 的 JDBC 操作本质上仍然是流操作：**写入数据库时由本地文件流向数据库传输；读取数据库时由数据库二进制流向本地文件传输。**

------

## JDBC 批处理

### 什么是 JDBC 批处理

**JDBC 批处理（Batch Processing）是指先将多次数据库操作加入一个批次，再统一提交执行。** 它主要适用于一次性执行大量结构相同或相近的 `INSERT`、`UPDATE`、`DELETE` 操作，可以减少 Java 程序与数据库之间频繁交互产生的开销。

例如，需要向商品表中插入大量数据：

```sql
CREATE TABLE t_product (
    id BIGINT PRIMARY KEY,
    name VARCHAR(255)
);
```

如果需要插入 10000 条商品记录，可以选择每准备一条数据就立即执行一次 SQL，也可以先将这些操作加入批次，再集中执行。

二者的核心区别可以理解为：

```text
不使用批处理：

准备第 1 条数据 → executeUpdate()
准备第 2 条数据 → executeUpdate()
准备第 3 条数据 → executeUpdate()
        ...
准备第 10000 条数据 → executeUpdate()
使用批处理：

准备第 1 条数据 → addBatch()
准备第 2 条数据 → addBatch()
准备第 3 条数据 → addBatch()
        ...
准备多条数据
        ↓
executeBatch()
```

------

### 不使用批处理

不使用批处理时，可以反复给同一个 `PreparedStatement` 设置不同参数，然后每循环一次调用一次 `executeUpdate()`：

```java
String sql =
        "insert into t_product(name) values(?)";

try (
        Connection conn = DBUtil.getConnection();
        PreparedStatement ps =
                conn.prepareStatement(sql)
) {
    int count = 0;

    for (int i = 1; i <= 10000; i++) {
        ps.setString(1, "product" + i);

        count += ps.executeUpdate();
    }

    System.out.println(
            "插入了" + count + "条记录"
    );
}
```

这里虽然始终复用了同一个 `PreparedStatement`，但循环中的每一条数据都会立即执行一次 `executeUpdate()`。实际代码也采用这种方式插入 10000 条记录，并记录整体执行时间。

其过程可以概括为：

```text
循环一次
   ↓
设置参数
   ↓
executeUpdate()
   ↓
执行一次数据库操作
   ↓
进入下一次循环
```

当数据量非常大时，这种频繁执行方式会产生较多的数据库交互开销。

------

### 使用批处理

使用批处理时，不再每设置一次参数就立即执行，而是调用 `addBatch()` 将当前这组参数对应的操作加入批次：

```java
ps.setString(1, "product" + i);
ps.addBatch();
```

准备完一批数据后，再调用：

```java
ps.executeBatch();
```

统一执行当前批次。

例如：

```java
String sql =
        "insert into t_product(name) values(?)";

try (
        Connection conn = DBUtil.getConnection();
        PreparedStatement ps =
                conn.prepareStatement(sql)
) {
    for (int i = 1; i <= 10000; i++) {
        ps.setString(1, "product" + i);
        ps.addBatch();
    }

    ps.executeBatch();
}
```

因此，使用 `PreparedStatement` 进行批处理时，最核心的两个方法是：

| 方法             | 作用                              |
| ---------------- | --------------------------------- |
| `addBatch()`     | 将当前参数对应的 SQL 操作加入批次 |
| `executeBatch()` | 执行当前已经积累的批处理操作      |

实际批处理代码中也是先反复调用 `addBatch()`，再通过 `executeBatch()` 提交执行。

------

### `addBatch()` 加入的是什么

使用 `PreparedStatement` 时，SQL 模板通常只定义一次：

```java
String sql =
        "insert into t_product(name) values(?)";
```

循环过程中不断改变的是占位符 `?` 对应的参数：

```java
ps.setString(1, "product1");
ps.addBatch();

ps.setString(1, "product2");
ps.addBatch();

ps.setString(1, "product3");
ps.addBatch();
```

可以将它理解为不断向批次中加入：

```text
SQL 模板：insert into t_product(name) values(?)

第 1 组参数：product1
第 2 组参数：product2
第 3 组参数：product3
...
```

最后调用 `executeBatch()`，统一执行已经积累的这些操作。

因此，**`addBatch()` 并不是立即执行 SQL，而是把当前这一次参数设置对应的操作加入待执行批次。**

------

### `executeBatch()` 的返回值

`executeBatch()` 的返回值是一个 `int[]`：

```java
int[] rows = ps.executeBatch();
```

数组中的元素用于表示批处理中各条命令的执行结果。

当前阶段重点掌握：

**`executeUpdate()` 用于执行一次更新操作，而 `executeBatch()` 用于执行一批已经通过 `addBatch()` 加入的操作。**

实际代码中也通过 `int[] rows = ps.executeBatch();` 接收批处理执行结果。

------

### 为什么批处理通常更快

大量数据写入时，批处理提高效率的主要原因是**减少重复的数据交互和执行开销**。

如果每条数据都单独执行：

```text
Java 程序
   ↓
发送第 1 次数据库操作
   ↓
数据库处理
   ↓
Java 程序
   ↓
发送第 2 次数据库操作
   ↓
数据库处理
   ↓
...
```

大量重复交互会不断产生网络通信和数据库执行相关开销。

使用批处理后，多条操作可以集中处理：

```text
Java 程序
   ↓
积累多组参数
   ↓
统一提交批次
   ↓
数据库集中处理
```

因此，批处理主要能够减少以下开销：

1. **减少 Java 程序与数据库之间频繁交互的次数。** 当数据库部署在远程服务器时，每一次请求都存在网络通信成本，大量单条执行会使这部分开销不断累积。
2. **使 JDBC 驱动和数据库有机会对一批结构相同的操作进行集中处理。** 相比逐条提交，批量执行通常更适合大量数据写入。

因此，在少量数据操作中，批处理带来的差异可能并不明显；而在几千条、几万条甚至更多数据的集中写入场景中，批处理的优势通常更加明显。

------

### MySQL 的 `rewriteBatchedStatements`

使用 MySQL Connector/J 进行批处理时，可以在 JDBC URL 中配置：

```
rewriteBatchedStatements=true
```

例如：

```text
jdbc:mysql://localhost:3306/jdbc?rewriteBatchedStatements=true
```

该配置用于启用 MySQL Connector/J 对批处理语句的相关优化。对于符合条件的批量 `INSERT`，驱动可以对提交方式进行优化，例如将多次同类插入组织成更加适合批量执行的形式。上传的批处理代码也明确配置该参数，并说明驱动会对批量 `INSERT` 进行优化。

可以从概念上理解为：

```text
原始多次 INSERT

INSERT INTO t_product(name) VALUES (?)
INSERT INTO t_product(name) VALUES (?)
INSERT INTO t_product(name) VALUES (?)
```

在符合条件的情况下，可以被驱动优化为类似：

```sql
INSERT INTO t_product(name)
VALUES (?), (?), (?);
```

这样能够进一步减少大量单条操作带来的开销。

> **注意**
>
> `rewriteBatchedStatements=true` 是 **MySQL Connector/J 的连接属性**，不是所有数据库 JDBC 驱动都使用这个参数。因此，应将它理解为 MySQL JDBC 批处理中的特定配置，而不是 JDBC 批处理本身的通用语法。

------

### 不要无限积累批次

虽然可以连续调用大量 `addBatch()` 后一次执行，但实际处理大量数据时，通常不应无限制地把所有操作都积累在内存中。

例如有 10000 条数据，可以每累计 1000 条执行一次：

```java
String sql =
        "insert into t_product(name) values(?)";

try (
        Connection conn = DBUtil.getConnection();
        PreparedStatement ps =
                conn.prepareStatement(sql)
) {
    for (int i = 1; i <= 10000; i++) {
        ps.setString(1, "product" + i);
        ps.addBatch();

        if (i % 1000 == 0) {
            ps.executeBatch();
        }
    }

    ps.executeBatch();
}
```

实际代码采用的就是**每累计 1000 条执行一次批处理**的方式。

这种处理方式的思路是：

```text
第 1～1000 条
      ↓
executeBatch()

第 1001～2000 条
      ↓
executeBatch()

第 2001～3000 条
      ↓
executeBatch()

      ...
```

这样既能够利用批处理减少频繁提交的开销，又可以避免一次积累过多待执行数据。

最后再执行一次 `executeBatch()`，主要是为了处理**最后不足一个完整批次的数据**。

例如总共有 10500 条数据，每 1000 条执行一次：

```text
前 10000 条
→ 已执行 10 个完整批次

剩余 500 条
→ 最后一次 executeBatch()
```

如果总记录数正好能够被批次大小整除，最后一次调用可能没有新的数据需要处理，但这种写法可以使代码适用于任意记录数量。

------

### 批处理完整流程

使用 `PreparedStatement` 执行大量插入时，可以整理为：

```java
String sql =
        "insert into t_product(name) values(?)";

try (
        Connection conn = DBUtil.getConnection();
        PreparedStatement ps =
                conn.prepareStatement(sql)
) {
    int batchSize = 1000;

    for (int i = 1; i <= 10000; i++) {
        ps.setString(1, "product" + i);

        // 将当前参数加入批次
        ps.addBatch();

        // 每累计一批就执行
        if (i % batchSize == 0) {
            ps.executeBatch();
        }
    }

    // 执行最后不足 batchSize 的剩余数据
    ps.executeBatch();
}
```

整个过程可以概括为：

```text
创建 PreparedStatement
        ↓
设置当前记录参数
        ↓
addBatch()
        ↓
是否达到批次大小？
   ↓否             ↓是
继续设置参数     executeBatch()
   ↑                ↓
   └────────────────┘
        ↓
循环结束
        ↓
执行剩余批次
```

## JDBC 事务

### 什么是事务

**事务（Transaction）是由一组相关数据库操作组成的一个完整业务单元，这组操作要么全部成功，要么全部失败。** 事务的作用是保证一组彼此关联的数据修改不会只执行一部分，从而维持数据的一致性和正确性。

例如银行转账业务：

```text
A 账户向 B 账户转账 10000 元
```

数据库中至少需要执行两条 `UPDATE`：

```sql
UPDATE t_act
SET balance = balance - 10000
WHERE act_no = 'act-001';
UPDATE t_act
SET balance = balance + 10000
WHERE act_no = 'act-002';
```

这两条 SQL 在业务上属于一个整体：

1. A 账户扣除 10000 元。
2. B 账户增加 10000 元。

如果第一条成功、第二条失败，就会出现 A 的钱已经扣掉，但 B 没有收到钱的情况，数据库虽然每一条 SQL 都可能单独执行正确，但**整个业务已经处于错误状态**。

因此，转账业务必须保证：

**两条 SQL 要么全部成功并提交，要么出现任何问题时全部撤销。**

这就是事务需要解决的问题。

> **结论**
>
> 事务管理的对象不是某一条独立 SQL，而是**一个完整业务中需要共同成功或共同失败的一组数据库操作**。

------

### 转账案例中的事务问题

假设从 `act-001` 向 `act-002` 转账：

```java
double amount = 10000.0;

String sql1 =
        "update t_act " +
        "set balance = balance - ? " +
        "where act_no = ?";

String sql2 =
        "update t_act " +
        "set balance = balance + ? " +
        "where act_no = ?";
```

如果直接按照普通 JDBC 方式执行：

```java
try (
        Connection conn = DBUtil.getConnection();
        PreparedStatement ps1 =
                conn.prepareStatement(sql1);
        PreparedStatement ps2 =
                conn.prepareStatement(sql2)
) {
    ps1.setDouble(1, amount);
    ps1.setString(2, "act-001");
    ps1.executeUpdate();

    ps2.setDouble(1, amount);
    ps2.setString(2, "act-002");
    ps2.executeUpdate();
}
```

代码看起来依次执行了两个账户更新，但这里存在一个严重问题：**JDBC 默认启用自动提交。**

------

### JDBC 默认自动提交

对于新获得的 `Connection`，JDBC 默认通常处于自动提交模式：

```java
conn.getAutoCommit() == true
```

自动提交意味着：

**每成功执行一条需要提交的 SQL，数据库就会自动提交一次事务。**

例如转账过程中先执行：

```java
ps1.executeUpdate();
```

A 账户余额已经更新后，这次修改可能立即被提交。

如果此时程序发生异常：

```java
System.out.println(10 / 0);
```

第二条 SQL 根本没有机会执行，那么结果就变成：

```text
A 账户：已经扣款
B 账户：没有收款
```

实际转账示例正是在第一条更新之后故意制造异常，此时由于没有进行事务控制，会出现只完成一半业务的情况。

因此，JDBC 默认自动提交适合彼此独立的简单数据库操作，但对于**多条 DML 必须作为一个整体完成的业务**，就必须手动控制事务。

> **易错点**
>
> “自动提交”并不是说 Java 程序结束后统一提交，而是通常在每一条 SQL 成功执行后就完成提交。因此多条 SQL 之间默认并没有天然形成一个不可分割的整体。

------

### JDBC 事务控制的三个核心操作

JDBC 中的事务主要通过 `Connection` 控制。

最核心的三个方法是：

| 方法                   | 作用                                   |
| ---------------------- | -------------------------------------- |
| `setAutoCommit(false)` | 关闭自动提交，开始由程序手动控制事务   |
| `commit()`             | 提交事务，使本次事务中的修改正式生效   |
| `rollback()`           | 回滚事务，撤销当前事务中尚未提交的修改 |

转账业务的基本流程可以整理为：

```text
获取 Connection
      ↓
关闭自动提交
      ↓
执行 A 账户扣款
      ↓
执行 B 账户加款
      ↓
全部成功？
   ↙         ↘
 是           否
 ↓             ↓
commit()    rollback()
```

源代码中同样通过 `conn.setAutoCommit(false)` 关闭自动提交，在业务成功后调用 `commit()`，发生异常时调用 `rollback()`。

------

### 关闭自动提交

事务开始前，首先关闭 JDBC 的自动提交：

```java
conn.setAutoCommit(false);
```

这意味着后续执行的 SQL 不再每执行一条就立即提交，而是先作为当前事务的一部分保留。

例如：

```java
Connection conn = DBUtil.getConnection();

conn.setAutoCommit(false);
```

从这之后执行的两次账户更新，就可以由同一个 `Connection` 统一控制提交或回滚。

> **注意**
>
> 同一个事务中的多条 SQL 必须使用**同一个 `Connection`**。事务状态是绑定在数据库连接上的，如果两条 SQL 分别使用不同连接，就不能通过一个 `commit()` 或 `rollback()` 统一控制它们。

------

### 提交事务

当完整业务中的所有 SQL 都成功执行后，调用：

```java
conn.commit();
```

提交事务。

提交之后，本次事务中的修改正式生效，不能再通过本次事务的 `rollback()` 撤销。

例如：

```java
ps1.executeUpdate();
ps2.executeUpdate();

conn.commit();
```

只有当两次账户更新都正常完成后才提交，因此能够保证：

```text
A 扣款成功
+
B 加款成功
        ↓
统一 commit()
```

源代码中的转账程序也是在两条 `UPDATE` 全部执行完成之后才调用 `conn.commit()`。

------

### 回滚事务

如果业务执行过程中出现异常，则调用：

```java
conn.rollback();
```

回滚当前事务。

例如：

```java
try {
    conn.setAutoCommit(false);

    ps1.executeUpdate();

    // 此处发生异常

    ps2.executeUpdate();

    conn.commit();

} catch (Exception e) {

    conn.rollback();
}
```

假设第一条 SQL 已经执行：

```text
A 账户余额暂时减少 10000
```

但还没有 `commit()`。

此时发生异常并调用 `rollback()`，数据库就会撤销当前事务中尚未提交的修改，使 A 账户恢复到事务开始前的状态。

因此：

```text
执行第一条 SQL
      ↓
尚未提交
      ↓
发生异常
      ↓
rollback()
      ↓
撤销第一条 SQL 的修改
```

最终能够保证转账业务不会只完成一半。

实际代码也在异常处理逻辑中调用 `conn.rollback()`，从而恢复事务中的修改。

------

### 转账事务的完整写法

结合 try-with-resources，可以将事务代码整理为：

```java
double amount = 10000.0;

String fromActNo = "act-001";
String toActNo = "act-002";

String sql1 =
        "update t_act " +
        "set balance = balance - ? " +
        "where act_no = ?";

String sql2 =
        "update t_act " +
        "set balance = balance + ? " +
        "where act_no = ?";

try (Connection conn = DBUtil.getConnection()) {

    try {
        // 1. 关闭自动提交
        conn.setAutoCommit(false);

        try (
                PreparedStatement ps1 =
                        conn.prepareStatement(sql1);

                PreparedStatement ps2 =
                        conn.prepareStatement(sql2)
        ) {
            // 2. A 账户扣款
            ps1.setDouble(1, amount);
            ps1.setString(2, fromActNo);
            int count1 = ps1.executeUpdate();

            // 3. B 账户加款
            ps2.setDouble(1, amount);
            ps2.setString(2, toActNo);
            int count2 = ps2.executeUpdate();

            if (count1 != 1 || count2 != 1) {
                throw new SQLException(
                        "转账失败，账户更新数量异常"
                );
            }

            // 4. 全部成功，提交事务
            conn.commit();
        }

    } catch (Exception e) {

        // 5. 出现异常，回滚事务
        try {
            conn.rollback();
        } catch (SQLException rollbackException) {
            rollbackException.printStackTrace();
        }

        throw e;

    } finally {

        // 6. 恢复连接的自动提交状态
        try {
            conn.setAutoCommit(true);
        } catch (SQLException e) {
            e.printStackTrace();
        }
    }

} catch (Exception e) {
    e.printStackTrace();
}
```

这段代码中的重点不是具体 SQL，而是事务边界：

```text
setAutoCommit(false)
        ↓
开始业务操作
        ↓
所有 SQL 成功
        ↓
commit()
```

出现任何异常：

```text
setAutoCommit(false)
        ↓
执行部分 SQL
        ↓
发生异常
        ↓
rollback()
```

源代码中的正确版本同样遵循“关闭自动提交 → 执行业务 → 成功提交 → 异常回滚”的基本流程。

------

### 为什么建议恢复 `autoCommit`

如果当前连接使用完成后立即真正关闭，那么连接销毁后其状态通常不会继续影响后续代码。

但实际项目中经常使用**数据库连接池**。调用 `close()` 时，连接可能并没有真正销毁，而是被归还连接池，之后还会被其他业务重新使用。

如果某个业务执行了：

```java
conn.setAutoCommit(false);
```

却没有恢复：

```java
conn.setAutoCommit(true);
```

那么下一个使用这条连接的业务可能拿到一个仍处于手动提交状态的连接，从而产生难以发现的问题。

因此，在需要兼顾连接复用的场景中，通常应在事务结束后恢复连接状态。

> **补充**
>
> 恢复 `autoCommit` 并不是事务提交本身的必需步骤，而是为了避免修改过的 `Connection` 状态影响后续复用者。尤其在连接池环境中，这一点更加重要。

------

### 回滚时要注意 `Connection` 是否为空

传统代码中经常这样声明：

```java
Connection conn = null;
```

然后在 `catch` 中直接：

```java
conn.rollback();
```

如果异常发生在成功获取连接之前，那么 `conn` 仍然是 `null`，此时调用 `rollback()` 会再次产生 `NullPointerException`。

因此传统写法应该判断：

```java
if (conn != null) {
    try {
        conn.rollback();
    } catch (SQLException e) {
        e.printStackTrace();
    }
}
```

使用 try-with-resources 并合理安排事务代码，可以减少这种资源管理问题。

------

### 事务中要检查 SQL 的执行结果

即使程序没有抛出异常，也不能完全说明业务一定成功。

例如：

```java
int count1 = ps1.executeUpdate();
int count2 = ps2.executeUpdate();
```

如果账户编号不存在，某条 `UPDATE` 可能返回 `0`，但不一定抛出异常。

对于转账业务来说，两条 SQL 都应该准确影响一条记录，因此可以判断：

```java
if (count1 != 1 || count2 != 1) {
    throw new SQLException("转账失败");
}
```

这样程序就可以进入异常处理逻辑并回滚事务。

> **注意**
>
> 事务保证的是“这组操作统一提交或统一回滚”，但事务并不会自动判断你的业务逻辑是否正确。程序仍然需要检查账户是否存在、余额是否充足、影响记录数是否符合预期等业务条件。

## JDBC 事务隔离级别

### 什么是事务隔离级别

当多个事务同时访问数据库时，它们之间可能发生相互影响。**事务隔离级别（Transaction Isolation Level）用于规定一个事务能够看到其他事务数据变化到什么程度。**

JDBC 通过 `Connection.setTransactionIsolation()` 设置当前连接的事务隔离级别。

例如：

```java
conn.setTransactionIsolation(
        Connection.TRANSACTION_SERIALIZABLE
);
```

源代码中也是通过 `setTransactionIsolation()` 设置隔离级别，并在之后关闭自动提交、开始事务。

JDBC 中定义了几个常用常量：

| JDBC 常量                                 | 隔离级别 |
| ----------------------------------------- | -------- |
| `Connection.TRANSACTION_READ_UNCOMMITTED` | 读未提交 |
| `Connection.TRANSACTION_READ_COMMITTED`   | 读已提交 |
| `Connection.TRANSACTION_REPEATABLE_READ`  | 可重复读 |
| `Connection.TRANSACTION_SERIALIZABLE`     | 串行化   |

隔离能力通常从上到下逐渐增强，同时并发性能通常会受到更多限制。

当前阶段重点掌握的是：**JDBC 可以通过 `Connection` 设置当前连接的事务隔离级别。**

例如：

```java
try (Connection conn = DBUtil.getConnection()) {

    conn.setTransactionIsolation(
            Connection.TRANSACTION_SERIALIZABLE
    );

    conn.setAutoCommit(false);

    // 执行业务

    conn.commit();
}
```

源码中也特别注明，隔离级别应在事务开始前设置。

> **注意**
>
> 具体数据库支持哪些隔离级别、默认隔离级别是什么，以及不同隔离级别如何处理脏读、不可重复读和幻读，需要结合数据库事务知识进一步学习。JDBC 在这里只负责提供统一的设置接口。

## 存储过程

### 什么是存储过程

**存储过程（Stored Procedure）是一组预先定义并保存在数据库中的 SQL 与流程控制逻辑，可以通过名称直接调用执行。** 它可以接收输入参数、返回输出参数，并在数据库服务器内部完成一系列数据处理操作。

存储过程本身并不是一种独立的通用编程语言，而是数据库提供的一种**过程化数据库编程机制**。除了普通 SQL 之外，通常还可以使用变量、条件判断、循环等流程控制结构，例如 `IF`、`WHILE`、`REPEAT` 等。

不同数据库对存储过程的语法和功能支持并不完全相同。例如 MySQL、Oracle、SQL Server 都支持存储过程，但各自使用的过程化 SQL 语法存在差异，因此存储过程通常具有较强的数据库平台依赖性。

------

### 存储过程的基本特点

普通 JDBC 程序通常由 Java 负责业务流程，并不断向数据库发送 SQL：

```text
Java 程序
    ↓
发送 SQL
    ↓
数据库执行
    ↓
返回结果
    ↓
Java 继续处理
    ↓
再次发送 SQL
```

如果某一段数据处理逻辑被封装成存储过程，则部分业务处理可以直接在数据库服务器内部完成：

```text
Java 程序
    ↓
调用存储过程
    ↓
数据库内部执行多步处理
    ↓
返回最终结果
```

因此，在某些需要连续执行多次数据库操作的场景中，存储过程可以减少应用程序与数据库之间反复交互的次数。

不过，**不能简单理解为“使用存储过程一定比 JDBC 执行 SQL 快”**。实际性能还受到 SQL 本身、索引、数据量、执行计划、数据库负载等多种因素影响。存储过程的优势之一是可以把一部分数据密集型处理集中到数据库内部，从而减少客户端与数据库之间的多次往返。

存储过程也存在明显缺点：

- 不同数据库的存储过程语法存在差异，**可移植性较差**；
- 业务逻辑写入数据库后，会使程序与具体数据库绑定得更加紧密；
- 数据库中同时承担大量复杂业务逻辑时，维护和调试成本可能增加。

因此，实际项目中通常不会因为“数据库操作多”就立即使用存储过程，而是根据具体业务、性能需求和项目架构决定是否采用。

> **结论**
>
> 存储过程的核心特点是：**将一组 SQL 和流程控制逻辑保存在数据库服务器中，由数据库直接执行。** 它可以减少某些场景下应用程序与数据库的频繁交互，但会提高程序与数据库平台之间的耦合。

------

### MySQL 存储过程示例

下面定义一个名为 `mypro` 的存储过程：

```sql
CREATE PROCEDURE mypro(IN n INT, OUT sum INT)
BEGIN
    SET sum := 0;

    REPEAT
        IF n % 2 = 0 THEN
            SET sum := sum + n;
        END IF;

        SET n := n - 1;
    UNTIL n <= 0
    END REPEAT;
END;
```

该存储过程的作用是：**计算从 `1` 到 `n` 之间所有偶数的和，并通过输出参数 `sum` 返回结果。**

其中定义了两个参数：

| 参数  | 参数类型 | 作用                           |
| ----- | -------- | ------------------------------ |
| `n`   | `IN`     | 输入参数，调用存储过程时传入   |
| `sum` | `OUT`    | 输出参数，由存储过程计算并返回 |

`IN` 表示参数主要用于向存储过程传递数据，`OUT` 表示参数主要用于把存储过程中的计算结果返回给调用者。

存储过程执行时，首先通过 `SET sum := 0` 初始化结果，然后使用 `REPEAT ... UNTIL` 循环逐渐减小 `n`。每次循环判断 `n % 2 = 0`，如果当前数字是偶数，就执行 `sum := sum + n`。

例如调用时传入 `n = 100`，最终得到：

```text
2 + 4 + 6 + ... + 100
```

计算结果通过 `sum` 输出。

> **补充**
>
> 在 MySQL 命令行等环境中创建包含多条语句的存储过程时，经常需要临时修改语句结束符，否则过程体内部的分号可能被客户端提前识别为整条 `CREATE PROCEDURE` 的结束位置。不同数据库工具对此处理方式可能不同。

## JDBC 调用存储过程

### `CallableStatement`

JDBC 专门提供了 `CallableStatement` 接口，用于调用数据库中的存储过程。

常见 JDBC 数据库操作对象可以简单区分为：

| 接口                | 主要用途         |
| ------------------- | ---------------- |
| `Statement`         | 执行普通 SQL     |
| `PreparedStatement` | 执行带参数的 SQL |
| `CallableStatement` | 调用存储过程     |

其中 `CallableStatement` 同样属于 JDBC 数据库操作接口体系。

调用存储过程时，基本流程为：

```text
获取 Connection
      ↓
准备存储过程调用语句
      ↓
prepareCall()
      ↓
获得 CallableStatement
      ↓
设置 IN 输入参数
      ↓
注册 OUT 输出参数
      ↓
execute()
      ↓
读取 OUT 参数
      ↓
释放资源
```

------

### 编写存储过程调用语句

调用前面定义的 `mypro`，JDBC 可以使用：

```java
String sql = "{call mypro(?, ?)}";
```

其中两个 `?` 分别对应：

```text
第 1 个 ? → IN 参数 n
第 2 个 ? → OUT 参数 sum
```

随后通过 `Connection.prepareCall()` 创建 `CallableStatement`：

```java
CallableStatement cs =
        conn.prepareCall(sql);
```

实际代码也是通过 `{call mypro(?, ?)}` 描述调用语句，再由 `conn.prepareCall(sql)` 创建 `CallableStatement`。

------

### 设置输入参数

输入参数的处理方式与 `PreparedStatement` 类似，可以通过 `setXXX()` 方法赋值。

例如：

```java
cs.setInt(1, 100);
```

表示给第一个 `?` 传入整数 `100`。

这里的参数索引仍然**从 `1` 开始**。

因此：

```text
mypro(?, ?)
      ↑
      第 1 个 ?
```

对应：

```java
cs.setInt(1, 100);
```

实际代码中也是使用 `cs.setInt(1, 100)` 为第一个输入参数赋值。

------

### 注册输出参数

输出参数不能使用普通的 `setXXX()` 赋值，而需要提前告诉 JDBC：

**这个位置是一个输出参数，并且返回的数据是什么 SQL 类型。**

例如：

```java
cs.registerOutParameter(
        2,
        Types.INTEGER
);
```

其中：

- `2` 表示第二个参数；
- `Types.INTEGER` 表示这个输出参数返回整数类型。

`Types` 是 `java.sql.Types` 类，其中定义了 JDBC 使用的各种 SQL 类型常量。

因此：

```text
mypro(?, ?)
         ↑
         第 2 个 ?
         OUT sum INT
```

对应：

```java
cs.registerOutParameter(
        2,
        Types.INTEGER
);
```

实际代码也是通过 `registerOutParameter(2, Types.INTEGER)` 注册第二个输出参数。

------

### 执行存储过程

完成输入参数设置和输出参数注册后，通过：

```java
cs.execute();
```

执行存储过程。

与前面学习的 JDBC 方法相比：

- `executeUpdate()` 常用于 `INSERT`、`DELETE`、`UPDATE`；
- `executeQuery()` 常用于 `SELECT`；
- 调用存储过程时可以使用 `execute()`。

实际代码中同样通过 `cs.execute()` 执行已经准备好的 `mypro`。

------

### 获取输出参数

存储过程执行结束后，可以通过对应的 `getXXX()` 方法读取输出参数。

由于第二个参数被注册为 `INTEGER`，因此可以使用：

```java
int sum = cs.getInt(2);
```

这里的 `2` 仍然表示调用语句中的第二个参数。

因此整个参数处理过程为：

```text
{call mypro(?, ?)}
             ↑   ↑
             │   │
             │   └── OUT sum
             │       registerOutParameter(2, Types.INTEGER)
             │       getInt(2)
             │
             └────── IN n
                     setInt(1, 100)
```

源代码中也是在执行存储过程后通过 `cs.getInt(2)` 读取最终计算结果。

------

### JDBC 调用存储过程完整示例

使用 try-with-resources 后，可以将代码整理为：

```java
import java.sql.CallableStatement;
import java.sql.Connection;
import java.sql.SQLException;
import java.sql.Types;

public class JDBCTest {

    public static void main(String[] args) {

        String sql = "{call mypro(?, ?)}";

        try (
                Connection conn =
                        DBUtil.getConnection();

                CallableStatement cs =
                        conn.prepareCall(sql)
        ) {
            // 设置 IN 参数
            cs.setInt(1, 100);

            // 注册 OUT 参数
            cs.registerOutParameter(
                    2,
                    Types.INTEGER
            );

            // 执行存储过程
            cs.execute();

            // 获取 OUT 参数
            int result = cs.getInt(2);

            System.out.println(
                    "计算结果：" + result
            );

        } catch (SQLException e) {
            e.printStackTrace();
        }
    }
}
```

这段程序执行的核心过程为：

1. 使用 `{call mypro(?, ?)}` 描述需要调用的存储过程。
2. 通过 `conn.prepareCall()` 获取 `CallableStatement`。
3. 通过 `setInt(1, 100)` 设置输入参数。
4. 通过 `registerOutParameter(2, Types.INTEGER)` 注册输出参数。
5. 调用 `execute()` 执行存储过程。
6. 通过 `getInt(2)` 获取数据库返回的计算结果。

## DAO

### 什么是 DAO

**DAO（Data Access Object，数据访问对象）是一种用于封装数据访问操作的设计思想。** DAO 类专门负责与数据库交互，例如执行 `INSERT`、`DELETE`、`UPDATE`、`SELECT`，而其他代码不直接编写 JDBC 数据访问细节。

例如员工管理系统中：

- `EmployeeDao` 负责员工数据；
- `UserDao` 可以负责用户数据；
- `ProductDao` 可以负责商品数据；
- `OrderDao` 可以负责订单数据。

如果没有 DAO，程序可能写成：

```text
界面输入
   ↓
业务判断
   ↓
获取 Connection
   ↓
编写 SQL
   ↓
PreparedStatement
   ↓
处理 ResultSet
   ↓
继续业务处理
```

界面、业务、数据库操作全部混合在一起。

引入 DAO 后可以变为：

```text
Client
   ↓
EmployeeDao
   ↓
JDBC
   ↓
数据库
```

`Client` 只表达“我要新增员工”“我要查询员工”，而至于 SQL 如何执行，则由 DAO 负责。

因此，DAO 的核心作用是**职责分离**：

**把数据库 CRUD 代码从其他程序逻辑中独立出来。**

这样做主要有两个好处：

1. **提高复用性。** 查询全部员工的代码只在 DAO 中编写一次，其他地方都可以调用。
2. **降低耦合。** 调用者只依赖 DAO 提供的方法，不需要关心底层 JDBC 代码如何实现。

## Employee 实体类

### Employee 的作用

数据库中一行员工记录，在 Java 程序中需要对应一个对象，因此定义 `Employee` 类负责封装员工数据。

这种类通常也称为 **PO（Persistent Object，持久化对象）**、实体类或者 JavaBean。

例如数据库记录：

| id   | name | job    | salary  |
| ---- | ---- | ------ | ------- |
| 1    | 张三 | 销售员 | 5000.00 |

可以转换为：

```java
Employee employee = new Employee();

employee.setId(1L);
employee.setName("张三");
employee.setJob("销售员");
employee.setSalary(new BigDecimal("5000.00"));
```

这样，程序后续就不需要一直操作散乱的 `id`、`name`、`job` 等变量，而可以统一操作一个 `Employee` 对象。

------

### Employee 完整代码

`emp.zip` 中的 `Employee` 如下：

```java
package com.jkweilai.emp.db.po;

import java.math.BigDecimal;
import java.util.Objects;

public class Employee {

    // 使用包装类型，可以接收 null
    private Long id;

    private String name;
    private String job;
    private String hireDate;
    private BigDecimal salary;
    private String address;

    public Employee() {
    }

    public Employee(
            Long id,
            String name,
            String job,
            String hireDate,
            BigDecimal salary,
            String address) {

        this.id = id;
        this.name = name;
        this.job = job;
        this.hireDate = hireDate;
        this.salary = salary;
        this.address = address;
    }

    public Long getId() {
        return id;
    }

    public void setId(Long id) {
        this.id = id;
    }

    public String getName() {
        return name;
    }

    public void setName(String name) {
        this.name = name;
    }

    public String getJob() {
        return job;
    }

    public void setJob(String job) {
        this.job = job;
    }

    public String getHireDate() {
        return hireDate;
    }

    public void setHireDate(String hireDate) {
        this.hireDate = hireDate;
    }

    public BigDecimal getSalary() {
        return salary;
    }

    public void setSalary(BigDecimal salary) {
        this.salary = salary;
    }

    public String getAddress() {
        return address;
    }

    public void setAddress(String address) {
        this.address = address;
    }

    @Override
    public String toString() {
        return "Employee{" +
                "id=" + id +
                ", name='" + name + '\'' +
                ", job='" + job + '\'' +
                ", hireDate='" + hireDate + '\'' +
                ", salary=" + salary +
                ", address='" + address + '\'' +
                '}';
    }

    @Override
    public boolean equals(Object o) {
        if (o == null || getClass() != o.getClass()) {
            return false;
        }

        Employee employee = (Employee) o;

        return Objects.equals(id, employee.id);
    }

    @Override
    public int hashCode() {
        return Objects.hashCode(id);
    }
}
```

这里有两个细节值得注意。

第一，`id` 使用 `Long` 而不是 `long`。新增员工时，主键还没有由数据库生成，因此程序需要能够创建：

```java
new Employee(
        null,
        name,
        job,
        hireDate,
        salary,
        address
);
```

基本类型 `long` 不能保存 `null`，而包装类 `Long` 可以。

第二，工资使用 `BigDecimal`，而不是 `double`。对于金额等需要精确十进制计算的数据，`BigDecimal` 比浮点类型更加合适。

## EmployeeDao 接口

### 为什么 DAO 还要定义接口

如果 `Client` 直接依赖具体类：

```java
EmployeeDaoImpl employeeDao =
        new EmployeeDaoImpl();
```

那么调用者和 `EmployeeDaoImpl` 直接绑定。

项目进一步定义：

```java
EmployeeDao
```

接口，然后让不同实现类实现它：

```text
             EmployeeDao
                  ↑
          ┌───────┴────────┐
          │                │
EmployeeDaoImpl     EmployeeDaoImpl2
```

调用者使用：

```java
EmployeeDao employeeDao =
        new EmployeeDaoImpl2();
```

变量依赖的是接口，具体实现则可以替换。

这体现的仍然是前面学习 JDBC 时反复出现的思想：

**面向接口编程，使调用者依赖规范，而不是直接依赖具体实现。**

------

### EmployeeDao 完整代码

```java
package com.jkweilai.emp.db.dao;

import com.jkweilai.emp.db.po.Employee;

import java.util.List;

public interface EmployeeDao {

    // 新增员工
    int insert(Employee employee);

    // 根据 id 删除员工
    int deleteById(Long id);

    // 根据 id 修改员工
    int updateById(Employee employee);

    // 查询全部员工
    List<Employee> selectAll();

    // 根据 id 查询员工
    Employee selectById(Long id);
}
```

这五个方法正好对应当前员工管理系统的五种数据库操作：

| DAO 方法       | 功能         |
| -------------- | ------------ |
| `insert()`     | 新增员工     |
| `deleteById()` | 删除员工     |
| `updateById()` | 修改员工     |
| `selectAll()`  | 查看员工列表 |
| `selectById()` | 查看员工详情 |

DAO 方法的命名通常直接体现数据库操作，例如 `insert`、`delete`、`update`、`select`，使方法职责更加清楚。

## 第一版 EmployeeDaoImpl

### 第一版 DAO 的实现方式

`EmployeeDaoImpl` 是这个项目中比较原始的一版 DAO。

它已经实现了职责分离：

```text
Client
   ↓
EmployeeDao
   ↓
EmployeeDaoImpl
   ↓
JDBC
```

但是 DAO 内部的每个方法仍然重复编写：

- 获取 `Connection`；
- 创建 `PreparedStatement`；
- 设置参数；
- 执行 SQL；
- 处理 `ResultSet`；
- 关闭资源；
- 处理 `SQLException`。

例如新增、删除、修改三个方法虽然 SQL 不同，但执行流程实际上非常相似。

这正是后面继续抽取 `BaseDao` 的原因。

------

### EmployeeDaoImpl 完整代码

```java
package com.jkweilai.emp.db.dao.impl;

import com.jkweilai.emp.db.dao.EmployeeDao;
import com.jkweilai.emp.db.po.Employee;
import com.jkweilai.emp.exception.AppException;
import com.jkweilai.jdbc.util.DBUtil;

import java.math.BigDecimal;
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

public class EmployeeDaoImpl implements EmployeeDao {

    @Override
    public int insert(Employee employee) {

        int count = 0;

        String sql =
                "insert into t_employee" +
                "(name,job,hire_date,salary,address) " +
                "values(?,?,?,?,?)";

        try (
                Connection conn =
                        DBUtil.getConnection();

                PreparedStatement ps =
                        conn.prepareStatement(sql)
        ) {
            ps.setString(
                    1,
                    employee.getName()
            );

            ps.setString(
                    2,
                    employee.getJob()
            );

            ps.setString(
                    3,
                    employee.getHireDate()
            );

            ps.setBigDecimal(
                    4,
                    employee.getSalary()
            );

            ps.setString(
                    5,
                    employee.getAddress()
            );

            count = ps.executeUpdate();

        } catch (SQLException e) {
            throw new AppException(
                    "数据库保存员工信息错误",
                    e
            );
        }

        return count;

    public int deleteById(Long id) {

        int count = 0;

        String sql =
                "delete from t_employee where id = ?";

        try (
                Connection conn =
                        DBUtil.getConnection();

                        conn.prepareStatement(sql)

            ps.setLong(1, id);

        } catch (SQLException e) {

            );
        }

    /**
     * 判断字符串是否为空。
     */
    private boolean isEmpty(String str) {
        return str == null || str.length() == 0;
    }

    /**
     * 只修改 Employee 中提供了有效值的属性。
     */
    @Override
    public int updateById(Employee employee) {

        Long id = employee.getId();

        if (id == null) {
            return 0;
        }

        String name =
                employee.getName();

        String job =
                employee.getJob();

        String hireDate =
                employee.getHireDate();

        BigDecimal salary =
                employee.getSalary();

        String address =
                employee.getAddress();

        if (
                isEmpty(name) &&
                isEmpty(job) &&
                isEmpty(hireDate) &&
                salary == null &&
                isEmpty(address)
        ) {
            return 0;
        }

        int count = 0;
        int isNotEmptyCount = 0;

        Map<Integer, Object> map =
                new HashMap<>();

        StringBuilder sb =
                new StringBuilder();

        sb.append(
                "update t_employee set "
        );

        if (!isEmpty(name)) {
            isNotEmptyCount++;

            sb.append("name=?,");

            map.put(
                    isNotEmptyCount,
                    employee.getName()
            );
        }

        if (!isEmpty(job)) {
            isNotEmptyCount++;

            sb.append("job=?,");

            map.put(
                    isNotEmptyCount,
                    employee.getJob()
            );
        }

        if (!isEmpty(hireDate)) {
            isNotEmptyCount++;

            sb.append("hire_date=?,");

            map.put(
                    isNotEmptyCount,
                    employee.getHireDate()
            );
        }

        if (employee.getSalary() != null) {
            isNotEmptyCount++;

            sb.append("salary=?,");

            map.put(
                    isNotEmptyCount,
                    employee.getSalary()
            );
        }

            isNotEmptyCount++;

            sb.append("address=?,");

            map.put(
                    isNotEmptyCount,
                    employee.getAddress()
            );
        }

        // 删除最后一个逗号，并追加 WHERE 条件
        String sql =
                sb.substring(
                        0,
                        sb.length() - 1
                ) +
                " where id = ?";

        try (
                Connection conn =
                        DBUtil.getConnection();

                PreparedStatement ps =
                        conn.prepareStatement(sql)
        ) {
            for (
                    int i = 1;
                    i <= isNotEmptyCount;
                    i++
            ) {
                ps.setObject(
                        i,
                        map.get(i)
                );
            }

            ps.setLong(

                    id
            );

            count = ps.executeUpdate();

        } catch (SQLException e) {
            throw new AppException(
                    "数据库保存员工信息错误",
                    e
            );
        }

        return count;
    }
```

### 第一版 DAO 中值得注意的修改操作

第一版 `updateById()` 并不是固定更新全部字段，而是根据 `Employee` 中哪些属性有值，**动态拼接 `UPDATE` SQL**。

例如：

```java
Employee employee =
        new Employee(
                10L,
                null,
                "项目经理",
                null,
                null,
                "北京海淀"
        );
```

程序只会拼接出类似：

```sql
UPDATE t_employee
SET job = ?, address = ?
WHERE id = ?;
```

而不会修改 `name`、`hire_date`、`salary`。

其核心过程是：

```text
读取 Employee 中的属性
          ↓
判断哪些属性有值
          ↓
动态追加 字段 = ?
          ↓
记录对应参数顺序
          ↓
最后追加 WHERE id = ?
          ↓
PreparedStatement 执行
```

因此第一版 DAO 已经包含一个相对复杂的**动态 SQL**案例。

## 为什么还需要 BaseDao

虽然第一版 `EmployeeDaoImpl` 已经把数据库操作从 `Client` 中分离出来，但是观察它的五个方法会发现大量重复代码。

例如 `insert()`、`deleteById()`、`updateById()` 最终都执行：

```java
ps.executeUpdate();
```

它们真正不同的只是：

- SQL 不同；
- `?` 对应的参数不同。

因此可以进一步抽象成：

```text
insert
delete
update
   ↓
共同逻辑
   ↓
BaseDao.executeUpdate()
```

查询同样如此。

`selectAll()` 与 `selectById()` 都需要：

```text
PreparedStatement
       ↓
executeQuery()
       ↓
ResultSet
       ↓
创建 Employee
       ↓
从结果集取数据
       ↓
给 Employee 属性赋值
```

因此可以继续思考：

**能不能连“把查询结果封装成 Java 对象”这件事情也抽成通用方法？**

`BaseDao` 就是在解决这个问题。

------

## BaseDao

### BaseDao 的职责

`BaseDao` 将 JDBC 中重复程度较高的操作抽取为三个通用方法：

| 方法              | 作用                                  |
| ----------------- | ------------------------------------- |
| `executeUpdate()` | 通用执行 `INSERT`、`DELETE`、`UPDATE` |
| `executeQuery()`  | 通用执行查询并封装多个对象            |
| `queryOne()`      | 查询最多一个对象                      |

这样，具体 DAO 不再关心如何创建 `PreparedStatement`、如何遍历 `ResultSet` 等通用流程。

------

### 通用 executeUpdate()

方法定义：

```java
public int executeUpdate(
        String sql,
        Object... params)
```

这里使用了**可变长参数**：

```java
Object... params
```

调用时可以传入任意数量的 SQL 参数：

```java
executeUpdate(
        sql,
        employee.getName(),
        employee.getJob(),
        employee.getSalary()
);
```

方法内部统一遍历：

```java
for (int i = 1; i <= params.length; i++) {
    ps.setObject(i, params[i - 1]);
}
```

这里存在两个不同的下标：

- JDBC 占位符编号从 `1` 开始；
- Java 数组下标从 `0` 开始。

因此第 `i` 个 JDBC 参数对应：

```
params[i - 1]
```

------

### 通用 executeQuery()

真正体现 `BaseDao` 设计思想的是：

```java
public <T> List<T> executeQuery(
        Class<T> clazz,
        String sql,
        Object... params)
```

这个方法同时使用了：

- 泛型；
- 可变长参数；
- `ResultSetMetaData`；
- 反射；
- `Class` 对象；
- `Field`。

目的只有一个：

**让同一个查询方法不仅能够查询 Employee，还能够查询其他 Java 对象。**

例如：

```java
executeQuery(
        Employee.class,
        sql
);
```

表示查询结果需要被封装成 `Employee`。

如果未来存在 `User`：

```java
executeQuery(
        User.class,
        sql
);
```

理论上同一个方法又可以把结果封装成 `User`。

------

### BaseDao 自动封装对象的原理

例如 SQL：

```sql
SELECT
    id,
    name,
    job,
    hire_date AS hireDate,
    salary,
    address
FROM t_employee;
```

首先通过：

```java
ResultSetMetaData metaData =
        rs.getMetaData();
```

获取结果集元数据。

然后取得每一列的标签：

```java
String fieldName =
        metaData.getColumnLabel(i);
```

得到：

```text
id
name
job
hireDate
salary
address
```

接下来通过反射：

```java
Field field =
        clazz.getDeclaredField(fieldName);
```

从 `Employee` 中寻找同名属性。

例如：

```text
查询结果列名        Employee 属性

id          →      id
name        →      name
job         →      job
hireDate    →      hireDate
salary      →      salary
address     →      address
```

然后调用：

```java
field.setAccessible(true);
```

允许通过反射直接访问私有属性。

读取一行结果后：

```java
T obj = clazz.newInstance();
```

动态创建一个 `Employee` 对象。

最后：

```java
field.set(
        obj,
        rs.getObject(field.getName())
);
```

把结果集中的数据写入对应属性。

于是完成：

```text
ResultSet
   ↓
ResultSetMetaData
   ↓
获取查询结果列名
   ↓
按照列名寻找 Java 属性
   ↓
反射创建对象
   ↓
反射给属性赋值
   ↓
Employee
```

------

### 为什么 SQL 中要使用别名

数据库字段是：

```
hire_date
```

Java 属性是：

```
hireDate
```

如果直接查询：

```sql
SELECT hire_date
FROM t_employee;
```

`getColumnLabel()` 得到的是 `hire_date`。

随后执行：

```java
clazz.getDeclaredField("hire_date");
```

但是 `Employee` 中不存在：

```java
private String hire_date;
```

只有：

```java
private String hireDate;
```

因此反射查找属性会失败。

解决办法是在 SQL 中使用别名：

```sql
SELECT hire_date AS hireDate
FROM t_employee;
```

此时：

```java
metaData.getColumnLabel(i)
```

得到 `hireDate`，刚好对应：

```java
private String hireDate;
```

> **注意**
>
> 当前 `BaseDao.executeQuery()` 能够自动封装对象的一个重要前提是：**查询结果中的列标签必须与 Java 对象的属性名一致。** 如果数据库字段和 Java 属性名称不同，就需要通过 `AS` 设置别名。

### BaseDao 完整代码

```java
package com.jkweilai.emp.db.dao.impl;

import com.jkweilai.emp.exception.AppException;
import com.jkweilai.jdbc.util.DBUtil;

import java.lang.reflect.Field;
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.ResultSetMetaData;
import java.sql.SQLException;
import java.util.ArrayList;
import java.util.List;

public class BaseDao {

    /**
     * 通用执行 INSERT、DELETE、UPDATE。
     */
    public int executeUpdate(
            String sql,
            Object... params) {

        int count = 0;

        try (
                Connection conn =
                        DBUtil.getConnection();

                PreparedStatement ps =
                        conn.prepareStatement(sql)
        ) {
            if (
                    params != null &&
                    params.length > 0
            ) {
                for (
                        int i = 1;
                        i <= params.length;
                        i++
                ) {
                    ps.setObject(
                            i,
                            params[i - 1]
                    );
                }
            }

            count = ps.executeUpdate();

        } catch (SQLException e) {
            throw new AppException(
                    "数据库更新失败",
                    e
            );
        }

        return count;
    }

    /**
     * 通用查询多个对象。
     */
    public <T> List<T> executeQuery(
            Class<T> clazz,
            String sql,
            Object... params) {

        List<T> list =
                new ArrayList<>();

        try (
                Connection conn =
                        DBUtil.getConnection();

                PreparedStatement ps =
                        conn.prepareStatement(sql)
        ) {
            if (
                    params != null &&
                    params.length > 0
            ) {
                for (
                        int i = 1;
                        i <= params.length;
                        i++
                ) {
                    ps.setObject(
                            i,
                            params[i - 1]
                    );
                }
            }

            try (
                    ResultSet rs =
                            ps.executeQuery()
            ) {
                ResultSetMetaData metaData =
                        rs.getMetaData();

                int columnCount =
                        metaData.getColumnCount();

                List<Field> fields =
                        new ArrayList<>();

                /*
                 * 根据查询结果列标签，
                 * 找到 Java 对象中对应的 Field。
                 */
                for (
                        int i = 1;
                        i <= columnCount;
                        i++
                ) {
                    String fieldName =
                            metaData.getColumnLabel(i);

                    Field field =
                            clazz.getDeclaredField(
                                    fieldName
                            );

                    field.setAccessible(true);

                    fields.add(field);
                }

                while (rs.next()) {

                    // 反射创建对象
                    T obj =
                            clazz.newInstance();

                    // 给对象属性赋值
                    for (Field field : fields) {

                        field.set(
                                obj,
                                rs.getObject(
                                        field.getName()
                                )
                        );
                    }

                    list.add(obj);
                }
            }

        } catch (
                SQLException |
                IllegalAccessException |
                InstantiationException |
                NoSuchFieldException e
        ) {
            throw new AppException(
                    "数据库查询异常",
                    e
            );
        }

        return list;
    }

    /**
     * 查询一个对象。
     */
    public <T> T queryOne(
            Class<T> clazz,
            String sql,
            Object... params) {

        List<T> list =
                executeQuery(
                        clazz,
                        sql,
                        params
                );

        if (
                list != null &&
                list.size() > 1
        ) {
            throw new AppException(
                    "查询结果条数 > 1，" +
                    "该方法只能返回一个结果！"
            );
        }

        return (
                list == null ||
                list.isEmpty()
        )
                ? null
                : list.get(0);
    }
}
```

> **补充**
>
> 当前源码使用 `clazz.newInstance()` 创建对象。这种写法在 JDK 8 中可以使用，但在较新的 Java 版本中已经被标记为过时，更现代的反射创建方式通常是 `clazz.getDeclaredConstructor().newInstance()`。这里应先理解项目源码的实现原理。

## 第二版 EmployeeDaoImpl2

### BaseDao 封装后的变化

有了 `BaseDao` 后，具体的 `EmployeeDao` 不再需要重复编写：

### 第一版和第二版 DAO 的区别

两版 DAO 的关系不是两个无关实现，而是在展示代码抽取前后的变化。

| 对比         | `EmployeeDaoImpl`   | `EmployeeDaoImpl2`          |
| ------------ | ------------------- | --------------------------- |
| JDBC 代码    | 每个方法自己编写    | 由 `BaseDao` 统一处理       |
| SQL          | 自己编写            | 自己编写                    |
| 参数         | 自己逐个 `setXXX()` | 传给 `executeUpdate()`      |
| 查询结果封装 | 手动创建 `Employee` | `BaseDao` 通过反射自动完成  |
| 代码量       | 较多                | 明显减少                    |
| 通用性       | 仅针对 `Employee`   | 公共部分可以供其他 DAO 复用 |

不过，两版 `updateById()` 的行为还有一个重要差异。

第一版支持**部分字段更新**，会根据属性是否为空动态拼接 SQL。

第二版固定执行：

```sql
UPDATE t_employee
SET
    name = ?,
    job = ?,
    hire_date = ?,
    salary = ?,
    address = ?
WHERE id = ?;
```

因此它要求待修改的 `Employee` 中提供完整字段值。

当前 `Client` 修改员工时会重新输入全部字段，因此第二版可以正常使用。

```java
                                name,
                                job,
                                hireDate,
                                new BigDecimal(
                                        salary
                                ),
                                address
                        );

                boolean success =
                        save(employee);

                System.out.println(
                        success
                                ? "录入成功"

                );

                list();

            } else if (no == 4) {

                // 修改员工
                list();

                System.out.println(
                        "您正在使用的功能是" +

                );

                System.out.print(
                        "请输入您要修改的员工的id："

                long id = sc.nextLong();

                String name = sc.next();

                System.out.print("岗位：");
                String job = sc.next();

                System.out.print("入职日期：");
                String hireDate = sc.next();

                System.out.print("月薪：");
                String salary = sc.next();

                System.out.print("住址：");
                String address = sc.next();

                Employee employee =
                        new Employee(
                                id,
                                name,
                                job,
                                hireDate,
                                new BigDecimal(
                                        salary
                                ),
                                address
                        );

                boolean success =
                        modify(employee);

                System.out.println(
                        success
                                ? "修改成功"
                                : "修改失败"
                );

            } else if (no == 5) {

                // 删除员工
                list();

                System.out.println(
                        "您正在使用的功能是" +
                        "根据id删除员工"
                );

                System.out.print(
                        "请输入删除的员工id："
                );

                long id = sc.nextLong();

                boolean success =
                        removeById(id);

                System.out.println(
                        success
                                ? "删除成功"
                                : "删除失败"
                );

            } else if (no == 0) {

                // 退出系统
                System.out.println("再见!!");

                System.exit(0);

            } else {

                System.out.println(
                        "您输入的功能编号有误！"
                );
            }
        }
    }

    /*
     * 当前这些方法仍然放在 Client 中。
     * 如果项目继续分层，可以进一步
     * 提取到业务层 Service。
     */

    private static boolean removeById(
            long id) {

        return employeeDao
                .deleteById(id) == 1;
    }

    private static boolean modify(
            Employee employee) {

        return employeeDao
                .updateById(employee) == 1;
    }

    private static boolean save(
            Employee employee) {

        return employeeDao
                .insert(employee) == 1;
    }

    private static void detailById(
            long id) {

        Employee employee =
                employeeDao.selectById(id);

        System.out.println(employee);
    }

    private static void list() {

        List<Employee> employees =
                employeeDao.selectAll();

        employees.forEach(
                System.out::println
        );
    }
}
```

## AppException

DAO 中的 JDBC 操作可能抛出 `SQLException`。

项目没有把每一个 `SQLException` 继续抛给 `Client`，而是定义了自己的运行时异常 `AppException`：

```java
package com.jkweilai.emp.exception;

public class AppException
        extends RuntimeException {

    public AppException(
            String message) {

        super(message);
    }

    public AppException(
            String message,
            Throwable cause) {

        super(
                message,
                cause
        );
    }

    public AppException(
            Throwable cause) {

        super(cause);
    }

    public AppException() {
        super();
    }
}
```

例如数据库更新失败时：

```java
catch (SQLException e) {
    throw new AppException(
            "数据库更新失败",
            e
    );
}
```

这样做以后，上层代码不需要到处处理 JDBC 专用的 `SQLException`，同时仍然通过 `cause` 保留了原始异常信息。

而不再关心通用 JDBC 流程。

## BaseDao 的本质

`BaseDao` 的核心实际上进行了两次抽象。

第一层抽象是**执行流程抽象**。

因为 `INSERT`、`DELETE`、`UPDATE` 最终都调用 `executeUpdate()`，所以统一封装成：

```java
executeUpdate(
        String sql,
        Object... params
)
```

第二层抽象是**结果封装抽象**。

普通 DAO 查询时需要手动执行：

```text
ResultSet
 ↓
new Employee()
 ↓
setId()
setName()
setJob()
...
```

`BaseDao` 使用：

- 泛型；
- `Class<T>`；
- `ResultSetMetaData`；
- 反射；

将其改造成：

```text
ResultSet
 ↓
读取列标签
 ↓
寻找同名 Field
 ↓
反射 new 对象
 ↓
反射赋值
 ↓
T
```

因此：

**`BaseDao` 不再知道自己查询的是员工、用户还是商品，它只按照查询结果列名和 Java 属性名之间的对应关系完成对象封装。**

这就是它能够成为“公共 DAO”的关键。

## JDBC 连接池

### 为什么需要连接池

`Connection` 是 JDBC 中表示数据库连接的对象。建立一个真正的数据库连接并不只是创建一个普通 Java 对象，底层通常还需要完成网络连接、数据库协议交互、身份认证以及数据库会话初始化等操作，因此数据库连接的创建和销毁成本相对较高。

如果每一次数据库操作都采用下面的方式：

```text
收到请求
   ↓
创建数据库连接
   ↓
执行 SQL
   ↓
关闭数据库连接
   ↓
下一次请求重新创建
```

会产生两个主要问题。

第一，**频繁创建和销毁数据库连接会影响程序效率。** 如果系统请求量较大，大量时间和资源会被消耗在数据库连接的建立和释放上，而不是实际 SQL 处理上。

第二，**如果数据库连接数量不受控制，可能给数据库服务器造成过大压力。** 假设短时间内出现大量并发请求，并且每个请求都自行创建数据库连接，就可能产生大量同时存在的数据库会话。当连接数量超过数据库能够承受的范围时，会导致请求失败，严重时甚至影响数据库服务的稳定性。

因此，需要解决两个问题：

**连接能不能重复利用，以及同时存在的连接数量能不能得到控制。**

数据库连接池就是为了解决这两个问题而产生的。

------

### 什么是数据库连接池

**数据库连接池（Connection Pool）是一种预先创建并集中管理数据库连接的机制。** 程序不再为每一次数据库操作重新创建连接，而是从连接池中获取已经准备好的连接，使用完成后再将连接归还连接池。

基本过程可以表示为：

```text
程序启动
   ↓
创建连接池
   ↓
预先准备一定数量的 Connection
   ↓
┌──────────────────────────┐
│       数据库连接池         │
│                          │
│ Connection 1  空闲        │
│ Connection 2  空闲        │
│ Connection 3  使用中      │
│ Connection 4  空闲        │
└──────────────────────────┘
   ↓
请求到来
   ↓
获取空闲 Connection
   ↓
执行数据库操作
   ↓
close()
   ↓
Connection 归还连接池
```

因此，连接池最重要的思想是：

**数据库连接不再“用一次就销毁”，而是“借出 → 使用 → 归还 → 再次利用”。**

------

### 连接池解决的问题

#### 提高连接复用率

没有连接池时：

```text
请求 1 → 创建连接 → 使用 → 销毁
请求 2 → 创建连接 → 使用 → 销毁
请求 3 → 创建连接 → 使用 → 销毁
```

使用连接池后：

```text
                  ┌→ 请求 1 使用 ─┐
Connection A ─────┤              ├→ 归还
                  └→ 请求 2 再使用
```

数据库连接可以被反复使用，从而减少频繁建立真实数据库连接所产生的开销。

#### 控制数据库连接数量

连接池通常会设置最大连接数。

例如：

```
maximumPoolSize = 20
```

意味着连接池允许管理的连接数量存在上限。当所有可用连接都已经被占用时，后续线程通常不能无限创建新连接，而是需要等待已有连接被归还；如果等待时间超过配置的最大等待时间，则会失败并抛出相应异常。

因此连接池实际上在应用程序和数据库之间增加了一层连接数量控制：

```text
大量业务线程
     ↓
   连接池
     ↓
最多 N 个数据库连接
     ↓
   MySQL
```

这可以防止应用程序无限制地创建数据库连接。

> **结论**
>
> 数据库连接池主要解决两个问题：**通过连接复用降低频繁创建连接的成本，通过限制连接数量保护数据库服务器。**

------

## DataSource

### `javax.sql.DataSource`

JDBC 提供了 `javax.sql.DataSource` 接口，用于抽象数据库连接的获取方式。主流 JDBC 连接池通常都会提供相应的 `DataSource` 实现。

因此程序可以面向：

```
javax.sql.DataSource
```

编程，而不需要直接依赖连接池内部如何管理连接。

例如：

```java
DataSource dataSource = ...;

Connection conn =
        dataSource.getConnection();
```

此时调用者只关心：

**通过 `DataSource` 获取一个 `Connection`。**

至于这个连接来自：

- Druid；
- HikariCP；
- DBCP；
- 其他连接池；

调用方通常不需要关心。

这种设计与 JDBC 前面学习过的面向接口编程思想完全一致：

```text
                 DataSource
                    ↑
           ┌────────┴────────┐
           │                 │
     DruidDataSource    HikariDataSource
```

调用者依赖的是统一接口 `DataSource`，具体连接池负责提供实现。

------

### 也可以自己实现连接池

由于 `DataSource` 是一个接口，因此理论上也可以自己定义类：

```java
public class ConnectionPool
        implements DataSource {

    @Override
    public Connection getConnection()
            throws SQLException {

        // 从自己维护的连接集合中
        // 获取可用连接
        return null;
    }

    // ...
}
```

前面的员工管理项目中已经出现过一个自定义 `ConnectionPool` 骨架，它实现的正是 `javax.sql.DataSource`，只是连接获取、归还、等待等核心逻辑尚未真正实现。

这说明连接池并不是 JDBC 中某一个固定类，而是一种数据库连接管理机制，而 `DataSource` 为这类机制提供了统一的 JDBC 接口。

## 连接池的常见配置

不同连接池产品的配置项名称并不完全一致，但基本连接池通常都需要解决以下几个问题：

```text
启动时创建多少连接？
        ↓
最多允许多少连接？
        ↓
空闲时保留多少连接？
        ↓
没有连接时最多等多久？
        ↓
如何判断连接是否仍然可用？
```

### 初始化连接数

初始化连接数表示连接池创建时预先建立多少数据库连接。

例如 Druid 中可以配置：

```
initialSize=5
```

表示连接池初始化时创建一定数量的连接。

不同连接池可能使用不同属性名，也可能采用不同的初始化策略，因此 `initialSize` 并不是所有连接池都统一使用的属性名称。

当前 Druid 示例配置中设置了 `initialSize=5`。

------

### 最大连接数

最大连接数限制连接池能够同时管理的连接数量。

例如 Druid：

```
maxActive=20
```

HikariCP：

```
maximumPoolSize=5
```

它们表达的核心含义类似：**连接池可以提供的连接数量存在上限。**

当前示例中的 Druid 最大连接数为 `20`，而 HikariCP 配置中的 `maximumPoolSize` 为 `5`。

当连接全部处于使用状态时：

```text
最大连接数 = 5

线程 1 → Connection 1
线程 2 → Connection 2
线程 3 → Connection 3
线程 4 → Connection 4
线程 5 → Connection 5
线程 6 → 没有空闲连接 → 等待
```

因此最大连接数是连接池控制数据库压力的重要参数。

------

### 最小空闲连接数

最小空闲连接数表示连接池希望至少保持多少个处于空闲状态、可以随时提供给业务线程的连接。

例如：

Druid 使用 `minIdle`；

HikariCP 使用 `minimumIdle`。

当前示例分别配置为：

```
minIdle=10
```

和：

```
minimumIdle=1
```

保留一定数量的空闲连接，可以让新的数据库请求到来时直接获得连接，而不必临时创建。

------

### 最大空闲连接数

部分连接池允许配置允许保留的最大空闲连接数量。

假设当前业务量下降，大量连接都处于空闲状态，如果全部长期保留，就可能浪费数据库资源。因此某些连接池允许超过一定空闲数量后释放多余连接。

需要注意，不同连接池对空闲连接的设计并不完全相同，因此不一定都会提供名为 `maxIdle` 的配置。

------

### 最大等待时间

如果连接池已经没有可以立即使用的连接：

```text
线程请求 Connection
      ↓
连接池已满
      ↓
所有 Connection 都在使用
      ↓
等待其他线程归还
```

连接池通常不会让线程无限等待，而是可以配置一个最大等待时间。

如果在规定时间内仍然没有获得连接，就会抛出异常。

不同连接池使用的属性名也不同，例如可能出现 `maxWait`、`connectionTimeout` 等名称。

------

### 连接有效性检查

数据库连接可能因为：

- 数据库服务器重启；
- 网络中断；
- 连接长期空闲；
- 数据库主动断开；

变成一个已经不可用的连接。

因此连接池通常需要提供连接有效性检测机制。

某些连接池中可以看到 `testOnBorrow`、`testOnReturn` 等配置，其含义大致是：

- 获取连接时是否检查连接是否有效；
- 归还连接时是否进行检查。

不同连接池的检查机制和配置名称并不完全相同，实际使用时需要结合具体连接池配置。

------

### 数据库连接信息

连接池最终仍然需要建立真实 JDBC 连接，因此还必须知道数据库连接信息，例如：

- JDBC URL；
- 用户名；
- 密码；
- JDBC 驱动。

只是以前这些配置供：

```java
DriverManager.getConnection(...)
```

使用，而现在由连接池根据配置创建和管理连接。

------

## 常见数据库连接池

Java 生态中常见或曾经广泛使用的数据库连接池包括 DBCP、c3p0、Druid、HikariCP、BoneCP 等。

### DBCP

DBCP 是 Apache 提供的数据库连接池实现，与 Apache/Tomcat 生态联系较为紧密。

其特点是历史较久、使用方式相对成熟，在一些传统 Java Web 项目中比较常见。

### c3p0

c3p0 也是较早被广泛使用的 Java 数据库连接池之一，提供连接管理、连接检查和连接恢复等能力。

在一些较老的 Java 项目以及早期 Hibernate 项目中可以看到它。

### Druid

Druid 是阿里巴巴开源的数据库连接池。

除了基本连接池能力之外，它还提供了较丰富的数据库访问监控和统计能力，因此它并不只是一个单纯的“连接存放容器”。

常见特点包括：

- 数据库连接池；
- SQL 统计；
- 数据源监控；
- SQL 访问相关扩展功能。

因此在一些希望同时进行数据库访问监控的项目中经常可以见到 Druid。

### HikariCP

HikariCP 更专注于**连接池本身的轻量化和性能**，核心目标相对单一，因此实现较为精简。

与 Druid 相比，可以简单理解为：

| Druid                                  | HikariCP                             |
| -------------------------------------- | ------------------------------------ |
| 除连接池外还提供较丰富的监控、统计功能 | 更专注于连接池本身                   |
| 功能较丰富                             | 相对轻量                             |
| 常用于需要数据库监控等能力的场景       | 常用于追求简洁、高性能连接管理的场景 |

实际项目选择哪一种连接池，并不能只根据“哪个更快”判断，还要结合使用的框架、已有技术体系、监控需求和项目配置决定。

### BoneCP

BoneCP 也是 Java 中曾经使用过的数据库连接池实现。当前学习阶段知道它属于连接池产品即可，不需要作为重点掌握。

> **结论**
>
> 当前阶段真正需要掌握的不是记住所有连接池产品，而是理解：**它们解决的问题基本相同，并且应用程序通常通过 `DataSource` 获取数据库连接。**

------

## Druid 的使用

### 配置 Druid

使用 Druid 时，首先需要将 Druid 相关依赖加入项目，然后准备连接池配置文件。

示例 `druid.properties`：

```properties
url=jdbc:mysql://localhost:3306/jdbc
username=root
password=123456
driverClassName=com.mysql.cj.jdbc.Driver
initialSize=5
minIdle=10
maxActive=20
```

当前 Druid 配置文件包含数据库地址、用户名、密码、驱动，以及 `initialSize`、`minIdle`、`maxActive` 等连接池参数。

------

### 创建 Druid DataSource

首先读取属性文件：

```java
InputStream in =
        DBUtil.class
                .getClassLoader()
                .getResourceAsStream(
                        "resources/druid.properties"
                );

Properties properties =
        new Properties();

properties.load(in);
```

再通过：

```java
DataSource dataSource =
        DruidDataSourceFactory
                .createDataSource(properties);
```

创建连接池。

完整核心逻辑可以整理为：

```java
InputStream in =
        DBUtil.class
                .getClassLoader()
                .getResourceAsStream(
                        "resources/druid.properties"
                );

Properties properties =
        new Properties();

properties.load(in);

DataSource dataSource =
        DruidDataSourceFactory
                .createDataSource(properties);
```

`dataSource` 就代表已经初始化完成的 Druid 数据源，也就是后续程序使用的连接池入口。

上传的 `DBUtil` 中已经保留了这一版 Druid 初始化代码，只是目前被注释掉。

------

### 从 Druid 中获取连接

连接池初始化完成后，获取连接统一使用：

```java
Connection conn =
        dataSource.getConnection();
```

与之前直接使用：

```java
DriverManager.getConnection(
        url,
        user,
        password
);
```

相比，调用方式已经发生变化。

以前：

```text
DBUtil
 ↓
DriverManager
 ↓
创建新的数据库连接
```

使用连接池以后：

```text
DBUtil
 ↓
DataSource
 ↓
连接池
 ↓
取得可用 Connection
```

这也意味着业务代码并不需要发生很大变化，因为最终得到的类型仍然是：

```
java.sql.Connection
```

## HikariCP 的使用

### 配置 HikariCP

HikariCP 同样可以通过属性文件配置。

当前 `hikaricp.properties` 为：

```properties
jdbcUrl=jdbc:mysql://localhost:3306/jdbc
username=root
password=123456
driverClassName=com.mysql.cj.jdbc.Driver
minimumIdle=1
maximumPoolSize=5
```

可以看到，HikariCP 与 Druid 的配置名称并不完全一样。

例如：

| 作用         | Druid       | HikariCP          |
| ------------ | ----------- | ----------------- |
| JDBC URL     | `url`       | `jdbcUrl`         |
| 最小空闲连接 | `minIdle`   | `minimumIdle`     |
| 最大连接数   | `maxActive` | `maximumPoolSize` |

因此，**连接池要解决的问题相似，但不同产品的属性名称不能混用。**

------

### 创建 HikariDataSource

首先读取配置：

```java
InputStream in =
        DBUtil.class
                .getClassLoader()
                .getResourceAsStream(
                        "resources/hikaricp.properties"
                );

Properties properties =
        new Properties();

properties.load(in);
```

然后创建 `HikariConfig`：

```java
HikariConfig config =
        new HikariConfig(properties);
```

最后创建连接池：

```java
DataSource dataSource =
        new HikariDataSource(config);
```

合起来就是：

```java
InputStream in =
        DBUtil.class
                .getClassLoader()
                .getResourceAsStream(
                        "resources/hikaricp.properties"
                );

Properties properties =
        new Properties();

properties.load(in);

HikariConfig config =
        new HikariConfig(properties);

DataSource dataSource =
        new HikariDataSource(config);
```

当前 `DBUtil` 实际启用的正是这套 HikariCP 初始化代码：类加载时读取 `hikaricp.properties`，然后创建 `HikariDataSource` 并保存到静态 `dataSource` 中。

------

## DBUtil 改造为连接池

### 原来的 DBUtil

没有连接池时，`DBUtil.getConnection()` 的核心逻辑是：

```java
Connection conn =
        DriverManager.getConnection(
                url,
                user,
                password
        );

return conn;
```

也就是说：

**每调用一次 `getConnection()`，都通过 `DriverManager` 建立一个新的数据库连接。**

这段旧逻辑目前仍然保留在 `DBUtil` 中，但是已经被注释。

------

### 使用连接池后的 DBUtil

有了连接池之后，`DBUtil` 中增加：

```java
private static DataSource dataSource;
```

类初始化时只创建一次连接池：

```java
static {
    InputStream in =
            DBUtil.class
                    .getClassLoader()
                    .getResourceAsStream(
                            "resources/hikaricp.properties"
                    );

    Properties properties =
            new Properties();

    try {
        properties.load(in);

        dataSource =
                new HikariDataSource(
                        new HikariConfig(
                                properties
                        )
                );

    } catch (Exception e) {
        throw new RuntimeException(e);
    }
}
```

之后所有业务代码获取连接统一调用：

```java
public static Connection getConnection()
        throws SQLException {

    return dataSource.getConnection();
}
```

当前代码的 `getConnection()` 已经从原来的 `DriverManager.getConnection()` 改为 `dataSource.getConnection()`。

因此 `DBUtil` 的演进可以表示为：

```text
最初：

业务代码
  ↓
DBUtil.getConnection()
  ↓
DriverManager
  ↓
创建新 Connection
现在：

业务代码
  ↓
DBUtil.getConnection()
  ↓
DataSource
  ↓
连接池
  ↓
获取可用 Connection
```

最大的好处是：

**DAO、Service 等上层代码完全不需要知道底层已经从普通 JDBC 连接切换成连接池。**

例如原来：

```java
Connection conn =
        DBUtil.getConnection();
```

改造连接池以后仍然是：

```java
Connection conn =
        DBUtil.getConnection();
```

变化被封装在 `DBUtil` 内部。

这正是封装带来的好处。

------

### 当前 DBUtil 使用的是哪个连接池

`DBUtil` 中同时保留了 Druid 和 HikariCP 两套初始化代码。

Druid 部分已经被注释：

```java
/*
static {
    ...
    dataSource =
            DruidDataSourceFactory
                    .createDataSource(
                            properties
                    );
}
*/
```

当前真正执行的是 HikariCP：

```java
static {
    ...
    dataSource =
            new HikariDataSource(
                    new HikariConfig(
                            properties
                    )
            );
}
```

因此：

**当前这份 `DBUtil` 实际使用的是 HikariCP，而不是 Druid。**

虽然测试类名称仍然叫做 `DruidTest`，但它最终调用的是：

```java
DBUtil.getConnection();
```

所以测试时真正从哪个连接池取连接，取决于 `DBUtil` 当前启用了哪一套 `DataSource` 配置。

## `Connection.close()` 的变化

### 不使用连接池时

如果直接通过：

```java
DriverManager.getConnection(...)
```

建立数据库连接，那么：

```java
conn.close();
```

通常意味着关闭对应的 JDBC 连接以及相关数据库资源。

------

### 使用连接池时

通过连接池获得的 `Connection` 通常不是让业务代码直接控制底层物理连接生命周期的简单对象，而是由连接池管理的连接对象或包装对象。

因此调用：

```java
conn.close();
```

时，通常不会简单地把底层物理数据库连接直接销毁，而是通知连接池：

**这个连接已经使用完成，可以重新变为空闲连接供其他请求使用。**

可以理解为：

```text
dataSource.getConnection()
        ↓
借出 Connection
        ↓
业务使用
        ↓
conn.close()
        ↓
归还连接池
        ↓
重新成为可用连接
```

当前 `DBUtil` 源码也特别说明，从连接池获取的 `Connection` 对底层真实连接进行了包装，然后通过统一的 `Connection` 接口提供给业务代码。

这也是为什么使用连接池以后，业务程序仍然必须调用：

```java
conn.close();
```

不能因为“连接要复用”就不关闭。

> **易错点**
>
> 使用连接池时，`close()` 更应该理解为**释放当前业务对连接的占用权并将其归还连接池**。如果一直不调用 `close()`，连接就可能长期处于“被占用”状态，其他线程无法继续使用，最终仍然可能导致连接池耗尽。

------

## 连接池并发测试

当前测试代码连续创建多个线程，每个线程都会：

1. 调用 `DBUtil.getConnection()` 获取连接；
2. 持有连接一段时间；
3. 最终执行 `conn.close()`。

核心代码为：

```java
class MyRunnable implements Runnable {

    @Override
    public void run() {

        Connection conn = null;

        try {
            conn =
                    DBUtil.getConnection();

            Thread.sleep(3000);

        } catch (Exception e) {
            throw new RuntimeException(e);

        } finally {

            if (conn != null) {
                try {
                    conn.close();

                } catch (SQLException e) {
                    throw new RuntimeException(e);
                }
            }
        }
    }
}
```

线程获得连接后会持有大约 3 秒，再通过 `close()` 释放连接。

测试程序首先创建 10 个线程，等待一段时间后又创建第二批 10 个线程。

而当前 HikariCP 配置中：

```
maximumPoolSize=5
```

即最大池大小设置为 `5`。

因此这个实验可以帮助理解：

```text
10 个线程同时请求连接
        ↓
连接池最大容量 = 5
        ↓
部分线程获得 Connection
        ↓
其他线程等待可用 Connection
        ↓
前面的线程 close()
        ↓
连接归还连接池
        ↓
等待线程继续获得连接
```

这正体现了连接池的两个作用：

**连接被重复利用，同时数据库连接数量受到连接池容量限制。**
