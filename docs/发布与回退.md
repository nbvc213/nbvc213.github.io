# 发布准备与回退

当前项目只在本地准备，以下是未来正式切换时使用的步骤，不代表已经执行部署。

## 本地准备

1. 确认 Java 21、Node.js 22，以及 config/site.yml 的正式根网址。当前仅支持账户根站点，不支持仓库子路径。
2. 依次运行 `npm.cmd run build`、`npm.cmd run test:content`、`npm.cmd run check:release`。
3. 查看 `.tools/release-report.json`：网址、笔记数量、文件数量、总体积及前端入口 SHA-256。报告在生成目录之外，不随站点发布。
4. 本地检查首页、搜索、长笔记、目录、代码、公式、图片、收藏及阅读设置。

发布目录检查阻止常见原稿、源码、环境文件、日志、个人备份、压缩包、源映射及符号链接。它按路径和文件类型检查，不能替代对笔记正文的保密与授权核对。

## 正式切换前保留的信息

- 原仓库及可恢复的提交记录，原网站源文件备份。
- Pages 原来的发布方式、分支和目录；首次切换前记录这些设置。
- 本次准备发布的提交标识、Actions 构建结果及 release-report。
- 浏览器个人记录需从书架导出备份；本地地址和正式域名是不同的存储空间。

## GitHub Actions 流程

默认分支推送后自动构建、检查并部署；PR只构建、检查，不部署。未来正式切换时，仓库 Pages 使用 GitHub Actions；手动运行网站工作流，在默认分支上勾选 publish，且构建及内容、发布目录检查全部通过后，部署任务才运行。

非默认分支即使勾选 publish，也不会执行部署任务。仓库默认分支不必固定叫 main，条件读取仓库配置。

本地没有执行过线上发布，本地通过不能代替远端 Linux 工作流验收。

## 发布后检查

确认正式域名首页、资源请求、分类、搜索跳转、旧地址和章节锚点，再检查手机尺寸与阅读设置。保留本次提交与工作流运行标识。

## 回退方案

如果此前已使用本项目发布：在默认分支通过新的回退提交恢复上一版已验证源码和配置，再运行完整检查及手动发布。不要仅回退 app.js；网页、搜索数据和资源必须属于同一版本。

如果是第一次从原 Jekyll 站切换：使用保留的原提交和配置，恢复切换前记录的 Pages 发布方式、分支、目录及原工作流，再核验正式域名。回退可能需要等待 Pages 构建完成。

回退源码不会撤销访问者浏览器中的收藏、偏好和批注；正文变更可能影响旧批注定位。实际线上回退尚未演练。
